## 1. 문제 — 질문 1자당 배경 5,371자

신규 세션에 **"너는 프롬프트 및 컨텍스트 엔지니어이다"(21자)** 한 줄을 보냈을 때 실측.

```
시스템 프롬프트           36,546자
  ├ 프롬프트 자산         16,359자 (45%)
  │   ├ global  15개      13,470자   ← 자산의 82%
  │   ├ role     2개       1,636자
  │   ├ project  1개         944자
  │   └ model    1개         309자
  └ 메모리·워크스페이스 등 20,187자 (55%)

도구 스키마(별도 PRD)      76,245자
─────────────────────────────────
합계                     112,791자 ≈ 37,000 토큰
사용자 질문                   21자
```

24시간 207회 컴파일 기준 시스템 프롬프트 **평균 34,967자 · 최대 40,423자**.
`casual` 인사말이든 `pipeline_runner` 장애 보고든 크기가 거의 같다 —
**질문에 따라 달라지지 않는다.**

첫 토큰까지 평균 **39.9초**, 턴 전체 중앙값 **254초**.

---

## 2. 가장 큰 낭비 — 26만 자를 조회해 2만 자만 쓴다

세션 `4841c4fb` 의 메모리 주입 실측.

```
injected_memory  266,966자
  ├ experience_memory  245,957자   ← 92%
  ├ long_term_memory    13,977자
  ├ observations         4,041자
  └ session_summaries    2,815자
```

**26만 자를 끌어와 2만 자로 잘라 넣는다.** 자르는 기준이 관련도가 아니라 크기라,
필요한 기억이 잘려나가고 필요 없는 것이 남을 수 있다. 조회 비용은 매 턴 그대로 든다.

---

## 3. 설계 원칙

1. **가져와서 자르지 말고, 찾아서 넣는다.** 절단은 무엇이 빠졌는지 모른다.
2. **질문을 먼저 읽는다.** 지금은 질문과 무관하게 같은 것이 실린다.
3. **항상 필요한 것과 가끔 필요한 것을 나눈다.** 규약·계약문은 상주, 사례·기억은 검색.
4. **계측 없이 줄이지 않는다.** 무엇이 줄었고 무엇이 깨졌는지 숫자로 말할 수 없으면
   되돌릴 근거도 없다.
5. **기존 경로를 지우지 않는다.** 환경변수로 켜고 끈다.

## 4. 단계

### 0단계 — 계측 (선행, 반나절)

지금은 `compiled_prompt_provenance` 에 **총량(`system_prompt_chars`)과 자산 목록**만
남는다. 자산 외 20,187자가 무엇인지 매 턴 기록되지 않는다.

구간별 자수를 provenance 에 추가한다.

```jsonc
"section_chars": {
  "assets": 16359,
  "memory_experience": 8200, "memory_long_term": 4100,
  "memory_observations": 900, "memory_summaries": 700,
  "workspace": 1200, "history": 5087
}
```

**이것이 1·2단계의 전제다.** 계측이 없으면 줄인 효과를 증명할 수 없다.

### 1단계 — 메모리 선검색 (효과 최대, 위험 최소)

```
현재:  질문 접수 → 메모리 266,966자 조회 → 20,187자로 절단 → 모델
개선:  질문 접수 → 의도·키워드 추출 → 관련 기억 상위 N건 검색 → 3,000자 내외 → 모델
```

`experience_memory` 가 92%를 차지하고, 이 영역은 임베딩 검색이 이미 붙어 있다
(`memory_recall` ↔ `knowledge_graph`). **전량 조회를 상위 N건 검색으로 바꾸는 것**이
작업의 핵심이다.

- 검색 결과가 비면 기존 방식으로 폴백한다.
- 폴백이 일어난 건수를 로그로 남겨 N 과 임계값을 튜닝한다.

예상: 메모리 구간 20,187자 → **3,000자 내외**.

### 2단계 — 자산 조건부 주입

global 자산 15개가 13,470자로 자산의 82%다. 전부가 매 턴 필요하지는 않다.

| 분류 | 처리 |
|---|---|
| 항상 필요 (응답 계약·보고 규약 등 3~4개) | 상주 |
| 상황 한정 (배포 게이트·E2E 검증·디자인 계약 등) | 해당 intent·작업에서만 |

판정은 **intent 와 최근 도구 사용**으로 한다. 사람이 매번 고르게 하지 않는다.

예상: 자산 구간 16,359자 → **6,000자 내외**.

### 3단계 — 히스토리 압축

턴당 히스토리 71~118개 메시지. 최근 N턴은 원문, 그 이전은 요약으로 대체한다.
`session_summaries` 가 이미 있으므로 **쓰는 쪽을 바꾸는 일**이다.

## 5. 예상 결과

| 구간 | 현재 | 목표 |
|---|---|---|
| 프롬프트 자산 | 16,359자 | 6,000자 |
| 메모리 | 20,187자 | 3,000자 |
| 도구 (별도 PRD) | 76,245자 | 9,773자 |
| **합계** | **112,791자 (≈37,000토큰)** | **약 19,000자 (≈6,300토큰)** |

토큰이 약 1/6 로 준다. 첫 토큰 지연과 계정 한도 소모가 같은 방향으로 움직인다.

## 6. 검증

| 항목 | 기준 |
|---|---|
| 구간별 자수 | 0단계 계측으로 전후 비교 가능 |
| 첫 토큰까지 | 현재 평균 39.9초 대비 단축폭 |
| 응답 품질 | 같은 질문 20건을 전후로 돌려 비교. **수치 없이 판단하지 않는다** |
| 기억 누락 | 폴백 발생률, "알던 것을 모른다"는 사례 수집 |
| 되돌리기 | 환경변수 한 줄 + 재기동으로 원복 |

---

## 7. 위험

| 위험 | 대응 |
|---|---|
| 필요한 기억이 검색에서 누락 | 검색 결과가 비면 기존 방식 폴백. 누락 건 로깅 후 튜닝 |
| 맥락 손실로 답변 품질 저하 | 20건 A/B 비교를 통과하기 전에는 켜지 않는다 |
| 조건부 자산이 필요한데 빠짐 | 빠진 상태로 나간 답변을 표본 검사. 규약 위반이 보이면 상주로 승격 |
| 계측 자체가 느려짐 | 기록은 턴이 끝난 뒤 백그라운드로 (`turn_timing` 과 같은 방식) |

---

## 8. 착수 순서

```
0단계 계측  →  1단계 메모리 선검색  →  (도구 PRD 적용)  →  2단계 자산  →  3단계 히스토리
```

**도구 쪽이 절대량으로는 더 크다**(76,245자 vs 36,546자). 대표님 지시대로 도구를
먼저 적용하되, 이 문서의 0단계 계측은 도구 작업의 효과를 재는 데도 쓰이므로
함께 넣는다.
