# 프론트 진단기 PRD — 측정하고, 원인을 지목하고, 회귀를 막는다

작성 2026-09-13 · 대상: `aads.newtalk.kr` 프론트 전반(대시보드 82개 라우트 + 채팅)
상위 문서: `AADS-BROWSER-AUTOMATION-PRD.md` §7 "두 개의 레인"

---

## 0. 요약

프론트에 문제가 생겼을 때 **우리는 CEO 가 말해줘야 안다.** 오늘 채팅 렌더링이
깨진 것도 CEO 가 `Minified React error #31` 을 붙여넣어 알았다. 서버는
HTTP 200 을 돌려주고 있었으므로 헬스체크는 전부 초록이었다.

느린 것도 마찬가지다. "느리다"는 체감은 있는데 **어디가 느린지 아무도 모른다.**
페이지가 늦게 뜨는 건지, API 가 늦게 오는 건지, API 를 순서대로 부르느라 늦는
건지 구분할 자료가 없다.

진단기를 만든다. 헤드리스 크롬으로 실제 페이지를 열어 **로딩 속도 · 데이터 속도
· 런타임 오류 · UI 결함**을 한 번에 재고, 기준선과 비교해 **나빠졌으면 배포를
막는다.**

측정만으로는 아무것도 개선되지 않는다. 그래서 네 가지를 같이 넣는다.

| | |
|---|---|
| **기준선** | 직전 성공 실행을 저장하고 비교한다 |
| **예산** | 임계치를 넘으면 실패다. "조금 느려짐"이 쌓이는 걸 막는다 |
| **원인 지목** | "느리다"가 아니라 "`/api/v1/ops/health-check` 가 2.7초" 로 |
| **게이트** | 배포 P0/P1 감시에 물려 회귀가 배포되지 않게 한다 |

## 1. 문제

### 1.1 프론트 고장을 우리가 먼저 알지 못한다

2026-09-13 채팅 세션 하나가 렌더링되지 않았다. 증상은 화면 전체가
"오류가 발생했습니다" 였고, 원인은 React 최소화 오류 #31 —
`object with keys {label, values}` 를 그대로 렌더하려 한 것이다.

이걸 **CEO 가 오류 문구를 붙여넣어서 알았다.** 그 전까지:

- 서버 헬스체크: 정상 (HTTP 200)
- 배포 상태: 성공
- 시각 QA: 통과

셋 다 초록인데 화면은 안 떴다. 셋 중 어느 것도 **브라우저에서 무슨 일이
벌어지는지** 보지 않기 때문이다.

### 1.2 시각 QA 는 로그인 화면을 채점하고 있었다

같은 날 발견했다. QA 브라우저가 인증 없이 페이지를 열어, `/`·`/chat`·`/ops`
세 장이 전부 로그인 화면이었다(스크린샷 4장이 23,241바이트로 바이트 동일).
감리 요약도 "로그인 UI" 라고 적고 있었다.

지금도 인증 없이 열면 이렇다.

```
/       HTTP 307   ttfb 0.68s
/chat   HTTP 307   ttfb 0.65s
/ops    HTTP 307   ttfb 0.95s
```

전부 리다이렉트다. **인증 없는 진단은 아무것도 진단하지 못한다.**

### 1.3 "느리다"를 분해할 수 없다

체감은 있는데 자료가 없다. 필요한 구분은 최소 네 가지다.

| 구분 | 질문 |
|---|---|
| 서버 응답 | TTFB 가 긴가 |
| 페이지 렌더 | JS 번들이 커서 늦게 그려지는가 |
| 데이터 도착 | API 하나하나가 느린가 |
| 호출 구조 | API 를 **순서대로** 불러서 합이 커지는가 |

넷째가 특히 안 보인다. 각 API 가 300ms 여도 열 개를 직렬로 부르면 3초다.
개별 API 로그만 보면 전부 "빠름"이다.

### 1.4 UI 결함을 사람 눈에만 의존한다

숨은 요소, 겹친 요소, 화면 밖 버튼은 스크린샷으로 안 보인다. 눌러도 반응이
없는 UI 가 있어도 "그런 것 같다" 수준에서 끝난다.

## 2. 왜 자체 레인인가

`AADS-BROWSER-AUTOMATION-PRD.md` §7 에서 레인을 갈랐다. 프론트 진단은
**원격 레인이 아니라 자체 레인**이다.

| | 원격 레인 (배달·은행) | **자체 레인 (프론트)** |
|---|---|---|
| 경로 | 서버 → WS → PC Agent → CDP → 크롬 | 서버에서 헤드리스 직접 |
| 왕복 | 6~25초 | 수십 ms |
| 봇 차단 | 통과 못 함 | 해당 없음 |
| 로그인 | 사람 개입 | 토큰 발급 → storage_state |
| CEO PC | 켜져 있어야 함 | 무관 |

왕복 비용이 없으므로 **원격 레인이 못 하는 것을 한다** — 82개 라우트 전수 검사,
매 배포 회귀 비교, 페이지당 수십 번의 계측.

컨테이너에 크로미움이 이미 있다(`151.0.7922.34`, `--no-sandbox` 로 기동 확인).
새로 깔 것이 없다.

## 3. 진단 범위

### 3.1 페이지 로딩 속도

Navigation Timing + Paint Timing 에서 뽑는다.

| 지표 | 의미 | 느릴 때 의심 |
|---|---|---|
| **TTFB** | 첫 바이트까지 | 서버·프록시 |
| **DOMContentLoaded** | HTML 파싱 완료 | 동기 스크립트 |
| **FCP** | 첫 픽셀 | 번들 크기, 폰트 |
| **LCP** | 주요 콘텐츠 | 이미지, 데이터 대기 |
| **load** | 전체 로드 | 누적 |
| **전송 바이트** | 문서+JS+CSS+이미지 | 번들 비대 |

### 3.2 데이터 로딩 속도

`/api/` 로 나가는 XHR·fetch 를 전부 기록한다. **이것이 이 진단기의 핵심**이다.

호출별로 남기는 것:

```
URL(쿼리 제거)   메서드   상태   시작(ms)   소요(ms)   응답 바이트
```

여기서 유도하는 것:

| 판정 | 근거 |
|---|---|
| **가장 느린 API** | 소요 상위 N — 개선 대상 1순위 |
| **직렬 호출** | 앞 호출 종료 후 다음이 시작 — 병렬화 여지 |
| **중복 호출** | 같은 URL 을 여러 번 — 캐시·중복 렌더 |
| **과대 응답** | 응답 바이트 상위 — 페이지네이션 필요 |
| **실패 호출** | 4xx·5xx·타임아웃 — 화면에 빈 칸으로 나타난다 |
| **데이터 대기 구간** | 마지막 API 종료 − FCP — 사용자가 빈 화면을 본 시간 |

마지막 줄이 체감 속도에 가장 가깝다. 페이지는 떴는데 내용이 안 채워진 시간이다.

### 3.3 런타임 오류

- `pageerror` — 잡히지 않은 예외
- `console` error/warning
- **React 최소화 오류 해독** — `#31`(객체를 자식으로 렌더), `#418`(hydration
  불일치) 등 번호를 사람이 읽을 문장으로 바꾼다. 1.1 이 정확히 이 경우다
- **에러 바운더리 발동** — "오류가 발생했습니다" 같은 대체 화면이 떠 있는지

### 3.4 네트워크 실패

`requestfailed` 와 4xx/5xx 응답을 전부 모은다. 정적 자산 404 는 화면이 떠도
깨진 상태다.

### 3.5 UI 결함

`browser_page_inspector.py` (§4.1 관측기) 의 수집 로직을 재사용한다.

- 크기 0 / `display:none` / `opacity:0` 인데 클릭 대상인 요소
- 다른 요소에 완전히 가려진 버튼
- 뷰포트 밖으로 밀려난 조작 요소
- 가로 스크롤 발생 여부(모바일 폭에서)

## 4. "개선되게" 만드는 장치

측정값을 쌓기만 하면 아무도 안 본다. 네 가지를 같이 넣는다.

### 4.1 기준선과 회귀 비교

실행마다 결과를 저장하고 **직전 성공 실행과 비교**한다.

```
/ops   LCP  1,840ms → 2,910ms   (+58%)   ← 회귀
       느린 API: /api/v1/ops/health-check  2,700ms (+1,900ms)
```

"느려졌다"가 아니라 **언제부터, 무엇 때문에** 를 말한다.

### 4.2 예산

절대 임계치를 둔다. 기준선 비교만 하면 **조금씩 나빠지는 것**을 못 잡는다.
매번 +5% 면 회귀로 안 잡히지만 열 번이면 1.6배다.

초기값(§7)은 현재 실측에서 잡고, 개선될 때마다 내린다. 예산은 올리지 않는다 —
올려야 할 이유가 생기면 그건 별도 의사결정이다.

### 4.3 원인까지 지목한다

진단 결과는 **다음 행동이 바로 나오는 형태**여야 한다.

```
나쁜 예   /ops 페이지가 느립니다 (3.4초)
좋은 예   /ops LCP 3.4초 — 데이터 대기 2.1초가 원인
          /api/v1/ops/health-check  2,700ms  (단독 최대)
          API 7건을 직렬 호출 — 병렬화 시 약 1.8초 단축 예상
```

### 4.4 배포 게이트

배포 P0/P1 감시 구간(5분)에 물린다. 예산 초과나 신규 런타임 오류가 있으면
배포를 성공으로 기록하지 않는다.

단, **처음부터 차단으로 켜지 않는다.** 초기에는 경고만 남기고 임계치를
실측으로 보정한 뒤 차단으로 올린다. 오탐으로 배포가 막히면 게이트 자체가
꺼지게 된다.

## 5. 설계

### 5.1 흐름

```
① 토큰 발급        서버 내부에서 create_token — argv 노출 없음
② storage_state    localStorage/cookie 에 심어 인증 상태 확보
③ 계측 부착        console · pageerror · request · response · requestfailed
④ 이동             goto → networkidle(상한 있음)
⑤ 수집             Navigation/Paint Timing + API 호출 목록 + DOM 관측
⑥ 판정             예산 대조 + 직전 실행 대비 회귀
⑦ 저장             DB 적재 + 리포트 출력
```

②가 없으면 1.2 가 반복된다. 진단기는 **로그인 화면을 진단 결과로 저장하지
않는다** — 상위 PRD §4.4 의 검증 원칙과 같다. 로그인 화면이 감지되면 그
페이지는 `auth_failed` 로 기록하고 지표를 남기지 않는다.

### 5.2 실행 모드

| 모드 | 대상 | 용도 |
|---|---|---|
| `--quick` | 핵심 5개 라우트 | 배포 게이트 |
| `--full` | 82개 전 라우트 | 야간 정기 |
| `--url <경로>` | 지정 | 개별 조사 |
| `--compare` | 저장된 직전 실행과 비교만 | 회귀 확인 |

### 5.3 인증 취급

- 토큰은 **컨테이너 안에서 발급**하고 stdin 으로만 오간다. argv 금지
- storage_state 파일은 0600
- 리포트·DB 에 토큰을 남기지 않는다. 요청 헤더는 기록하지 않는다
- 쿼리스트링은 URL 정규화 시 제거한다(토큰이 실려 올 수 있다)

## 6. 데이터 모델

```
frontend_diagnostic_runs
  id, started_at, finished_at, mode, release_sha, pages_total,
  pages_ok, pages_failed, verdict(pass|warn|fail), summary jsonb

frontend_diagnostic_pages
  run_id, route, status(ok|auth_failed|error|timeout),
  ttfb_ms, dcl_ms, fcp_ms, lcp_ms, load_ms, transfer_bytes,
  api_calls int, api_total_ms, api_slowest_ms, api_slowest_url,
  data_wait_ms, serial_chain_ms, console_errors, page_errors,
  failed_requests, detail jsonb

frontend_diagnostic_findings
  run_id, route, severity(critical|major|minor), category, title,
  evidence jsonb
```

`detail` 에 API 호출 목록 원본을 넣는다. 요약만 남기면 나중에 원인을 되짚을 수
없다.

## 7. 판정 기준 (초기 예산)

실측으로 보정하기 전 출발값이다. 첫 `--full` 실행 뒤 P75 기준으로 다시 잡는다.

| 지표 | 경고 | 실패 |
|---|---|---|
| TTFB | 600ms | 1,500ms |
| FCP | 1,800ms | 3,000ms |
| LCP | 2,500ms | 4,000ms |
| 데이터 대기 | 1,000ms | 3,000ms |
| 단일 API | 800ms | 2,500ms |
| 전송 바이트 | 2MB | 5MB |
| 단일 API 응답 | 512KB | 2MB |
| 콘솔 오류 | 1건 | — |
| 잡히지 않은 예외 | — | 1건 |
| 에러 바운더리 발동 | — | 1건 |
| 실패 요청(4xx/5xx) | 1건 | 3건 |

**런타임 오류는 경고 단계를 두지 않는다.** 예외 하나면 그 화면은 이미 깨진
것이고, 1.1 이 그 경우였다.

회귀 판정은 별도다 — 직전 실행 대비 LCP·데이터 대기가 **30% 또는 500ms 이상**
나빠지면 회귀로 본다(둘 다 충족).

## 8. 대상 페이지

대시보드 라우트가 82개다. 전부 같은 빈도로 볼 필요는 없다.

| 등급 | 라우트 | 빈도 |
|---|---|---|
| **핵심** | `/`, `/chat`, `/ops`, `/tasks`, `/project-status` | 배포마다 |
| 주요 | `/decisions`, `/handovers`, `/reports`, `/memory`, `/projects` 등 | 매일 |
| 전체 | 나머지 | 주 1회 |

`/chat` 은 세션 파라미터가 있어야 실제 렌더 경로를 탄다. **1.1 이 특정 세션에서만
터졌다** — 목록 화면만 보면 못 잡는다. 대표 세션 id 를 고정 지정한다.

## 10. 한계

- **디자인 품질은 판단하지 않는다.** 정렬·여백·색이 "이상한지"는 시각 QA 감리의
  몫이다. 진단기는 "깨졌는지"와 "느린지"만 본다
- **헤드리스는 실제 사용자 환경이 아니다.** 서버에서 재는 값이라 네트워크 지연이
  빠진다. 절대값보다 **회귀 비교**에 쓴다
- **로그인 이후 상태만 본다.** 로그인 흐름 자체의 문제는 별도 과제다
- **실행 상호작용은 최소다.** 클릭해서 열리는 화면, 무한 스크롤 이후는 초기
  범위에 넣지 않는다
