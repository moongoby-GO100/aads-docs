# 웹 자동화 실행 방식 PRD — 관측 우선 루프

작성: 2026-09-13 · 대상: PC Agent 브라우저 브릿지 기반 자동화 전반
(GenSpark 수집, 신한 EasyView 간편조회, 배달 매출 수집, 시각 QA)

## 1. 문제

오늘 GenSpark 자동화를 실제로 돌리면서 세 가지가 드러났다. 셋 다 특정
사이트의 문제가 아니라 **실행 방식 자체의 문제**다.

### 1.1 왕복 비용이 지배한다

같은 브릿지로 명령별 왕복 시간을 직접 쟀다.

| 명령 | 왕복 |
|---|---|
| `browser_navigate` | 6.4 ~ 8.4초 |
| `browser_click` / `browser_fill` | 약 6초 |
| `browser_press_key` | 11.7초 |
| `browser_get_text` | 11.5 ~ 24.9초 |
| `browser_screenshot` | 6.5 ~ 7.4초 |
| `browser_health` | 22.4초 |

경로가 `서버 → WebSocket → PC Agent → CDP → 크롬` 이고 결과가 역순으로
돌아온다. **작업 내용과 무관한 고정 비용**이다.

로그인 한 번(입력 2 + 키 1 + 클릭 1 + 확인 2)에 약 67초가 걸렸다. 은행
간편조회처럼 15~25단계짜리 작업이면 **왕복 대기만 4~6분**이다. 실제 브라우저가
일하는 시간보다 대기가 압도적이다.

### 1.2 좌표는 창 크기가 바뀌면 깨진다

모델 선택 배지를 누르려다 네 번 헛짚었다. 그중 한 번은 이것 때문이었다.

```
스크린샷   1280 x 805
실제 뷰포트 1920 x 945     ← 1.5배 차이
```

스크린샷에서 읽은 좌표 (176, 634) 로 클릭하니 배지가 아니라 **생성된 이미지
영역**이 눌렸다. 스크린샷은 축소 저장되는데 `elementFromPoint` 는 실좌표를
받는다. 좌표를 쓰는 한 창 크기·DPI·줌이 바뀔 때마다 전부 다시 맞춰야 한다.

### 1.3 실패가 조용하다

세 가지가 전부 "성공"으로 보였다.

- **숨은 요소 클릭** — 셀렉터는 맞는데 화면에 없으면 클릭이 아무 일도 하지
  않고 `success` 를 돌려준다
- **프로그램 클릭 무시** — CDP/JS 로 만든 클릭은 `isTrusted=false` 다. 이걸
  요구하는 컴포넌트는 반응하지 않으면서 오류도 내지 않는다
- **엉뚱한 화면 저장** — GenSpark 대화 수집기는 세션이 끊긴 뒤 **로그인 화면을
  2,406건 "대화"로 저장**했다(4월 적재 2,422건 중 99%). 3월에는 17,456건 중
  92%가 실제 대화였으므로 어느 시점부터 조용히 고장난 것이다. 숫자는 쌓이니
  겉보기에는 정상이었다

세 경우 모두 **실패했다는 사실 자체가 어디에도 남지 않았다.**

## 2. 지금 방식의 한계

현재는 "셀렉터를 짐작해서 명령 하나 보내고, 결과를 스크린샷으로 확인하고,
틀리면 다시 짐작"하는 순환이다. 왕복이 6~25초이므로 **시행착오 한 번이 곧
수십 초**다. 오늘 배지 하나에 네 번 헛짚어 2분 넘게 썼다.

배치 기구가 이미 있는데 쓰이지 않는다. `browser_recipes` 테이블에
`login_steps` / `navigation_steps` / `capture_rules` 를 묶어 등록하는 구조가
있고, 등록된 것은 두 건뿐이다.

```
delivery.ddangyo.sales_collect   로그인 3단계 + 탐색 3단계
ohvis.login.basic                로그인 3단계 + 탐색 1단계
```

신한 EasyView 용은 없다. 그래서 은행 수집기는 개별 명령으로 돌며 왕복 비용을
전부 누적한다.

## 3. 설계 — 관측 우선 루프

방식을 바꾼다. **짐작하고 실행**에서 **관측하고 계획하고 실행**으로.

```
   ┌─────────────────────────────────────────────┐
   │  ① 관측   페이지 전체를 한 번에 분석         │
   │           (조작 가능 요소 + 안정 셀렉터)      │
   ├─────────────────────────────────────────────┤
   │  ② 계획   목표에 필요한 단계를 셀렉터로 확정  │
   │           실행 전에 전부 결정한다             │
   ├─────────────────────────────────────────────┤
   │  ③ 실행   묶어서 보낸다 (레시피 / eval 배치)  │
   ├─────────────────────────────────────────────┤
   │  ④ 검증   기대한 화면이 맞는지 확인            │
   │           아니면 저장하지 않고 사유를 남긴다   │
   └──────────────┬──────────────────────────────┘
                  │ 페이지가 바뀌었으면
                  └──────► ① 로 돌아간다
```

핵심은 **①을 먼저 한다**는 것과 **④에서 검증 없이 넘어가지 않는다**는 것이다.

### 3.1 관측 — 왕복 1회로 전체 파악

`scripts/browser_page_inspector.py` (구현 완료, `9eb0b962`).

한 번의 `browser_eval` 로 버튼·입력·링크·role 요소를 모두 수집한다. 실측으로
한 호출에 **34~55개 요소**를 확보했다.

```
$ browser_page_inspector.py --inspect
  뷰포트 1920x945 · 조작 가능 요소 34개
  - button:submit  "재생성"
      div.moa-image-result > div.generated-images
      > div.image-container.model-gpt-image-2 > div.edit-buttons-wrapper:nth-of-type(3) > button
```

세 가지 원칙을 지킨다.

**좌표를 쓰지 않는다.** `nth-of-type` 까지 포함한 CSS 경로를 만든다. 클래스만
쓰면 같은 모양이 여러 개일 때 구분되지 않는다. 이 경로는 창 크기와 무관하다.

**보이지 않는 요소를 거른다.** 크기 0, `display:none`, `visibility:hidden`,
`opacity:0` 을 제외한다. 1.3의 "숨은 요소 클릭"을 원천에서 막는다.

**화면 안/밖을 구분해 표시한다.** 화면 밖 요소는 스크롤이 먼저 필요하다는
뜻이므로 계획 단계에서 그 단계를 넣을 수 있다.

### 3.2 사람 클릭 기록 — 자동화가 못 찾는 요소의 해법

같은 도구가 클릭 기록기를 함께 심는다. 사람이 누른 요소의 셀렉터가 남는다.

```
$ browser_page_inspector.py --clicks
  [18:42:11] 사람 DIV "Nano Banana 2 Flash Lite"
      div.input-wrapper > div.model-selector > ...
```

`isTrusted` 를 함께 기록하는 것이 중요하다. **프로그램 클릭에 반응하지 않는
컴포넌트를 구분할 유일한 근거**다. 사람 클릭으로는 열리는데 프로그램 클릭으로
안 열리면 그 컴포넌트는 신뢰 이벤트를 요구하는 것이고, 셀렉터를 알아도
자동화할 수 없다. 그 판정을 추측이 아니라 데이터로 한다.

이동할 때마다 다시 심는다. 새로고침으로 사라지는 문제를 없앤다.

### 3.3 실행 — 묶어서 보낸다

관측에서 셀렉터가 전부 확정됐으므로 단계를 묶을 수 있다.

- **레시피**(`browser_recipes`) — 로그인·탐색·캡처를 한 묶음으로 등록해 한
  번에 실행. 왕복이 20회에서 2~3회로 준다
- **`browser_eval` 배치** — 레시피로 표현 안 되는 부분은 JS 한 덩어리로 묶어
  한 왕복에 처리. 오늘 이미지 6장을 이 방식으로 한 번에 받아왔다

### 3.4 검증 — 저장하기 전에 확인한다

1.3의 세 번째 실패가 가장 위험하다. 잘못된 것을 성공으로 기록하면 아무도
모른다.

거부 조건을 명시한다. `scripts/genspark_conversation_collector.py` 가 이
패턴의 구현이다.

```
로그인 화면 문구  → 저장 안 함, 사유 기록
봇 검증 화면      → 저장 안 함, 사유 기록
본문이 너무 짧음   → 저장 안 함, 사유 기록
전부 건너뜀       → exit 3 (조용한 성공 금지)
```

**부분 실패를 실패로 단정하지는 않는다.** 오탐이 나면 정상 수집까지 막힌다.
수치를 남겨 사람이 판단하게 한다.

## 4. 페이지 전이 — 같은 루프를 다시 돈다

다음 페이지가 나오면 **①부터 다시** 한다. 이전 페이지의 셀렉터를 그대로
쓰지 않는다.

전이 판정은 이렇게 한다.

| 신호 | 의미 |
|---|---|
| URL 변경 | 명백한 전이 — 재관측 필수 |
| 조작 요소 집합이 크게 달라짐 | SPA 내 화면 전환 — 재관측 필수 |
| 요소 수가 같고 셀렉터도 동일 | 같은 화면 — 재관측 생략 가능 |

SPA 는 URL 이 안 바뀌어도 화면이 갈린다. 그래서 URL 만 보면 안 되고 **요소
집합을 지문처럼 비교**해야 한다.

관측 1회가 6~15초이므로, 시행착오 한 번(6~25초)보다 싸다. **의심스러우면
재관측한다**가 기본값이어야 한다.


## 4.5 세션 수명 관리

로그인이 자동화의 관문이라면, 세션 유지가 **작업 길이의 상한**을 정한다.

### 무조작 타임아웃은 활동으로 갱신된다

국내 은행의 10분 제약은 *무조작* 기준이다. 조작이 이어지면 갱신된다. 따라서
"10분 안에 전부 끝내라"가 아니라 **"10분 이상 놀지 마라"**가 맞는 제약이다.

이 차이가 설계를 바꾼다.

```
잘못된 전제   로그인 → 10분 안에 급하게 완료
맞는 전제     로그인 → 활동을 이어가며 장시간 운용
```

계좌별·기간별 조회를 연달아 돌리면 그 작업 자체가 갱신 신호가 된다. 급하게
끝낼 필요가 없다.

### 그래도 확인해야 하는 세 가지

| 항목 | 왜 |
|---|---|
| **절대 세션 한도** | 활동과 무관하게 30~60분에서 끊는 곳이 있다. 갱신이 안 되므로 중간 재로그인 지점을 설계에 넣어야 한다 |
| **연장 확인 팝업** | "세션을 연장하시겠습니까?" 가 뜨고 클릭을 요구한다. 셀렉터만 알면 자동으로 누를 수 있으므로 오히려 유리하다 |
| **keep-alive 탐지** | 의미 없는 요청을 주기적으로 찍으면 자동화로 잡힐 수 있다. 실제 조회 작업 자체를 간격으로 삼는다 |

### 설계

```
① 사람이 로그인 (보안키보드가 있으면 불가피)
② 로그인 완료 감지 → 자동 트리거
③ 작업 수행 — 조회를 연달아 돌려 세션을 살린다
④ 연장 팝업이 뜨면 눌러 연장
⑤ 로그인 화면이 나오면 즉시 중단, 저장하지 않음
```

④가 장기 운용의 핵심이다. ⑤는 3.4 의 검증 원칙과 같다 — 세션이 끊긴 뒤의
화면을 결과로 저장하면 4월의 로그인 화면 2,406건이 반복된다.

## 4.6 문서에서 빠져 있던 것들

오늘 실제로 부딪혔으나 위에 담기지 않은 항목이다. 설계 없이 두면 각각이
조용한 실패 지점이 된다.

### (a) PC Agent 오프라인 시 헤드리스로 조용히 강등된다

브라우저 브릿지의 폴백 사슬이 이렇다.

```
pc_bridge → headless → http_api → container_health
```

실제로 `PC_AGENT_OFFLINE` 상태의 세션이 `kind=headless` 로 남아 있는 것을
확인했다. 문제는 **헤드리스가 봇 차단을 통과하지 못한다**는 점이다. GenSpark
는 헤드리스에 로그인 화면조차 주지 않고 검증 페이지만 준다.

즉 PC Agent 가 꺼지면 자동화가 멈추는 게 아니라 **쓸모없는 결과를 계속
만들어낸다.** 4월 수집기 고장과 같은 형태다.

→ PC Agent 가 필요한 작업은 `require_pc_agent` 를 명시하고, 헤드리스로
  강등되면 실행하지 말고 중단한다.

### (b) iframe 내부는 현재 셀렉터로 잡히지 않는다

관측기는 최상위 문서만 훑는다. GenSpark 에서 iframe 3개를 확인했고, 은행은
조회 영역이 iframe 인 경우가 흔하다. 프레임 타깃팅이 없으면 "요소가 없다"로
끝난다 — 실제로는 있는데 못 보는 것이다.

### (c) 다단계 인증은 사람을 기다려야 한다

은행은 흐름 중간에 OTP·ARS·추가 인증을 요구한다. 자동화가 그 자리에서
실패로 끝내면 세션이 버려진다. **인증 대기 상태를 인지하고 멈춰서 사람을
기다린 뒤 이어가는** 경로가 필요하다.

### (d) 팝업·새 탭

은행은 조회 결과를 새 창으로 띄우는 경우가 많다. `browser_tabs` 로 목록은
얻을 수 있으나, 어느 탭이 대상인지 고르고 전환하는 규칙이 설계에 없다.

### (e) 다운로드 파일은 PC 에 떨어진다

거래내역은 엑셀·CSV 다운로드가 흔하다. `browser_download` 가 있지만 파일은
**CEO PC 에 저장되고 AADS 서버에는 없다.** 회수 경로가 필요하다. 오늘
이미지는 `fetch` + base64 로 우회했는데(6장 확보), 대용량 파일에는 맞지 않는다.

### (f) 실패 재시도 정책 — 금융은 다르다

일반 사이트는 재시도가 싸다. 은행은 **로그인 실패가 누적되면 계정이 잠긴다.**
같은 재시도 정책을 쓰면 안 된다. 인증 관련 실패는 재시도 금지가 기본이어야
한다.

### (g) 동시 실행 금지

`yeoljeong_bank_collector_harness.py` 에 `financial_exclusive` 레인이 이미
있다. 금융 작업은 한 번에 하나만 돌아야 한다. 브라우저 세션이 하나뿐이므로
동시 실행은 서로의 화면을 망가뜨린다.

### (h) 자격증명 취급 규칙

오늘 지킨 것을 규칙으로 남긴다.

- Vault 에서 읽어 **프로세스 안에서만** 쓴다
- argv 에 싣지 않는다(프로세스 목록 노출)
- 로그·stdout 에 출력하지 않는다. 성공/실패만 남긴다
- 화면 캡처에 값이 찍힐 수 있으므로 인증 화면 캡처는 최소화한다

### (i) 감사 기록

`authenticated_collector_audit_log` 가 있으나 실행 기록이 없다(설정 등록 5건
뿐). **무엇을, 언제, 어느 계정으로 조회했는지** 남지 않으면 금융 자동화로서
성립하지 않는다.

### (j) 스크린샷은 축소 저장된다

1920x945 화면이 1280x805 로 저장된다(1.5배). 사람이 눈으로 확인할 때는

## 6. 적용 순서

1. **관측기 도입** — 완료(`9eb0b962`). 모든 신규 자동화는 여기서 시작한다
2. **신한 EasyView 레시피 등록** — 가장 큰 효과. 관측기로 셀렉터를 뽑아
   `browser_recipes` 에 등록한다. 왕복 20회 → 2~3회.
   착수 전에 4.6 (a)(f)(i) 를 먼저 넣는다 — 헤드리스 강등 차단, 금융 재시도
   금지, 감사 기록. 셋 다 없으면 조용한 실패나 계정 잠금으로 돌아온다
3. **기존 수집기에 검증 가드 추가** — GenSpark 수집기는 완료. 배달·시각 QA 도
   같은 가드가 필요하다
4. **전이 판정 자동화** — 요소 집합 지문 비교를 관측기에 넣는다

2번이 은행 건의 직접 해결이고, 3번이 "조용한 실패" 재발 방지다.

## 7. 남은 것과 한계

- **신뢰 이벤트를 요구하는 컴포넌트는 자동화할 수 없다.** GenSpark 모델
  드롭다운이 이 경우로 의심된다. 3.2 의 기록으로 판정할 수 있지만, 판정이
  "불가"로 나오면 우회가 아니라 **사람이 한 번 누르는 절차**로 설계해야 한다
- **왕복 비용 자체는 줄지 않는다.** 이 설계는 왕복 횟수를 줄이는 것이지
  한 번의 6~25초를 줄이지 못한다. PC Agent 통신 구간 최적화는 별도 과제다
- **관측기가 못 잡는 요소가 있다.** Shadow DOM 은 현재 수집되지 않는다.
  iframe 은 4.6 (b) 로 별도 과제화했다
