## 0. 요약

배달 수집 30일 실측 **성공률 9.2%**(4,873건 중 449건). 그런데 그 449건마저
대부분 파싱 없이 원문을 저장한 **가짜 성공**이었다.

원인은 특정 사이트가 아니라 실행 방식이다. **셀렉터를 짐작해 명령 하나 보내고
스크린샷으로 확인하고 틀리면 다시 짐작**하는 순환이, 왕복 6~25초짜리 채널 위에서
돌고 있다. 시행착오 한 번이 곧 수십 초이고, 그래서 앞 회차가 안 끝난 채 다음
스케줄이 뜨고(중복 실행 1,576건), 실패해도 조용히 성공으로 기록된다.

**짐작하고 실행**에서 **관측하고 계획하고 실행하고 검증**으로 바꾼다.

### 1.2 "성공" 449건의 정체 — 파싱 없이 원문을 넷에 복사

성공 건의 `counts` 를 보면 네 카테고리(매출·리뷰·정산·광고) 건수가 **전부 같은
값**인 행이 있다. 파싱하지 않은 페이지 원문 하나를 네 카테고리에 그대로 복사해
넣었다는 신호다.

```
coupangeats  {"ads": 212, "sales": 212, "reviews": 212, "settlements": 212}
yogiyo       {"ads": 104, "sales": 104, "reviews": 104, "settlements": 104}
baemin       {"ads": 0,   "sales": 1,   "reviews": 0,   "settlements": 1}   ← 실제 파싱
```

전수로 세면 이렇다.

| 서비스 | 성공 | 전 카테고리 동일 | 비율 |
|---|---:|---:|---:|
| coupangeats | 50 | **50** | 100% |
| yogiyo | 87 | **84** | 97% |
| baemin | 310 | 4 | 1.3% |
| ddangyo | 2 | 0 | 0% |

**요기요·쿠팡이츠에는 파서가 없다.** 있는 것처럼 `succeeded` 만 기록됐다.
실질 성공은 449건이 아니라 **315건, 성공률 6.5%** 다.

이것이 4월 GenSpark 수집기 고장(세션 끊긴 뒤 로그인 화면 2,406건을 "대화"로
저장, 그 달 적재의 99%)과 **같은 형태**다. 숫자는 쌓이니 겉보기에 정상이다.

### 1.3 왕복 비용이 지배한다

같은 브릿지로 명령별 왕복 시간을 직접 쟀다.

| 명령 | 왕복 |
|---|---|
| `browser_navigate` | 6.4 ~ 8.4초 |
| `browser_click` / `browser_fill` | 약 6초 |
| `browser_press_key` | 11.7초 |
| `browser_get_text` | 11.5 ~ 24.9초 |
| `browser_screenshot` | 6.5 ~ 7.4초 |
| `browser_health` | 22.4초 |

경로가 `서버 → WebSocket → PC Agent → CDP → 크롬` 이고 결과가 역순으로 온다.
**작업 내용과 무관한 고정 비용**이다.

로그인 한 번(입력 2 + 키 1 + 클릭 1 + 확인 2)에 약 67초. 은행 간편조회처럼
15~25단계면 **왕복 대기만 4~6분**이다. 실제 브라우저가 일하는 시간보다 대기가
압도적이다. `ATTEMPT_TIMEOUT` 160건이 여기서 나온다.

### 1.4 중복 실행 1,576건 — 최다 실패

최다 실패가 사이트 문제가 아니다. **앞 회차가 안 끝났는데 다음 스케줄이 뜬
것**이다. 회차가 §1.3 때문에 길어지고, 스케줄은 그걸 모른 채 정시에 돈다.

기전을 확인했다. 배달 수집 스케줄이 **네 개**이고 대상 서비스가 겹친다.

| job id | 주기 | 대상 |
|---|---|---|
| `delivery_auto_collect` | 07·12·18시 | 전체 |
| `delivery_auto_collect_baemin_full_backfill` | 02:30·14:30·22:30 | baemin |
| `delivery_auto_collect_pc_agent_catchup` | **10분 간격** | baemin |
| `delivery_auto_collect_coupangeats_catchup` | **15분 간격** | coupangeats |

`max_instances=1` 은 **같은 job id 의 중복만** 막는다. baemin 은 세 개, coupangeats
는 두 개의 서로 다른 job 이 노린다. 이들이 하나의 수집 잠금을 두고 다툰다.

중복 건수가 정확히 그 구조를 따른다.

```
coupangeats  679   (15분 간격 + 정시)
baemin       631   (10분 간격 + 정시 + 백필)
ddangyo      139
yogiyo       127
```

한 회차가 §1.3 때문에 10분을 넘기면, 10분 간격 job 은 그 사실을 모른 채 다음
회차를 낸다. 중복은 두 번 해롭다 — 자기가 실패하고, 겹친 동안 **다른 정상
작업까지 차단**한다. 페이지 분석을 아무리 잘해도 이건 해결되지 않는다.
**스케줄 설계 문제**다.

### 1.5 좌표는 창 크기가 바뀌면 깨진다

모델 선택 배지를 누르려다 네 번 헛짚었고, 그중 한 번은 이것 때문이었다.

```
스크린샷   1280 x 805
실제 뷰포트 1920 x 945     ← 1.5배 차이
```

스크린샷 좌표 (176, 634) 로 클릭하니 배지가 아니라 **생성된 이미지 영역**이
눌렸다. 스크린샷은 축소 저장되는데 `elementFromPoint` 는 실좌표를 받는다.
좌표를 쓰는 한 창 크기·DPI·줌이 바뀔 때마다 전부 다시 맞춰야 한다.

## 3. 지금 방식의 한계

현재는 "짐작 → 명령 1개 → 스크린샷 확인 → 틀리면 다시 짐작"이다. 왕복이
6~25초이므로 **시행착오 한 번이 곧 수십 초**다. 오늘 배지 하나에 네 번 헛짚어
2분 넘게 썼다.

배치 기구는 이미 있는데 쓰이지 않는다. `browser_recipes` 에
`login_steps` / `navigation_steps` / `capture_rules` 를 묶어 등록하는 구조가
있고, 등록된 것은 두 건뿐이다.

```
delivery.ddangyo.sales_collect   로그인 3단계 + 탐색 3단계
ohvis.login.basic                로그인 3단계 + 탐색 1단계
```

신한 EasyView 용은 없다. 그래서 은행 수집기는 개별 명령으로 돌며 왕복 비용을
전부 누적한다.

## 4. 설계 — 관측 우선 루프

```
   ┌─────────────────────────────────────────────┐
   │  ① 관측   페이지 전체를 한 번에 분석         │
   │           (조작 가능 요소 + 안정 셀렉터)      │
   ├─────────────────────────────────────────────┤
   │  ② 계획   목표에 필요한 단계를 셀렉터로 확정  │
   │           실행 전에 전부 결정한다             │
   ├─────────────────────────────────────────────┤
   │  ③ 실행   묶어서 보낸다 (레시피 / eval 배치)  │
   ├─────────────────────────────────────────────┤
   │  ④ 검증   기대한 화면이 맞는지 확인            │
   │           아니면 저장하지 않고 사유를 남긴다   │
   └──────────────┬──────────────────────────────┘
                  │ 페이지가 바뀌었으면
                  └──────► ① 로 돌아간다
```

핵심은 **①을 먼저 한다**와 **④에서 검증 없이 넘어가지 않는다**이다.

### 4.1 관측 — 왕복 1회로 전체 파악

`scripts/browser_page_inspector.py` (구현 완료 `9eb0b962`).

한 번의 `browser_eval` 로 버튼·입력·링크·role 요소를 모두 수집한다. 실측으로
한 호출에 **34~55개 요소**를 확보했다.

```
$ browser_page_inspector.py --inspect
  뷰포트 1920x945 · 조작 가능 요소 34개
  - button:submit  "재생성"
      div.moa-image-result > div.generated-images
      > div.image-container.model-gpt-image-2 > div.edit-buttons-wrapper:nth-of-type(3) > button
```

세 가지 원칙.

**좌표를 쓰지 않는다.** `nth-of-type` 까지 포함한 CSS 경로를 만든다. 클래스만
쓰면 같은 모양이 여러 개일 때 구분되지 않는다. 이 경로는 창 크기와 무관하다
(§1.5 해결).

**보이지 않는 요소를 거른다.** 크기 0, `display:none`, `visibility:hidden`,
`opacity:0` 을 제외한다. "숨은 요소 클릭 후 success" 를 원천에서 막는다.

**화면 안/밖을 구분한다.** 화면 밖 요소는 스크롤이 먼저 필요하다는 뜻이므로
계획 단계에서 그 단계를 넣는다.

### 4.2 사람 클릭 기록 — 자동화가 못 찾는 요소의 해법

같은 도구가 클릭 기록기를 함께 심는다. 사람이 누른 요소의 셀렉터가 남는다.

```
$ browser_page_inspector.py --clicks
  [18:42:11] 사람 DIV "Nano Banana 2 Flash Lite"
      div.input-wrapper > div.model-selector > ...
```

`isTrusted` 를 함께 기록하는 것이 중요하다. **프로그램 클릭에 반응하지 않는
컴포넌트를 구분할 유일한 근거**다. 사람 클릭으로는 열리는데 프로그램 클릭으로
안 열리면 그 컴포넌트는 신뢰 이벤트를 요구하는 것이고, 셀렉터를 알아도
자동화할 수 없다. 그 판정을 추측이 아니라 데이터로 한다.

이동할 때마다 다시 심는다. 새로고침으로 사라지는 문제를 없앤다.

### 4.3 실행 — 묶어서 보낸다

관측에서 셀렉터가 전부 확정됐으므로 단계를 묶을 수 있다.

- **레시피**(`browser_recipes`) — 로그인·탐색·캡처를 한 묶음으로 등록해 한 번에
  실행. 왕복이 20회에서 2~3회로 준다
- **`browser_eval` 배치** — 레시피로 표현 안 되는 부분은 JS 한 덩어리로 묶어 한
  왕복에 처리. 오늘 이미지 6장을 이 방식으로 한 번에 받아왔다

### 4.4 검증 — 저장하기 전에 확인한다

§2의 유형 A가 가장 위험하다. 잘못된 것을 성공으로 기록하면 아무도 모른다.

거부 조건을 명시한다. `scripts/genspark_conversation_collector.py` 가 이 패턴의
구현이다.

```
로그인 화면 문구  → 저장 안 함, 사유 기록
봇 검증 화면      → 저장 안 함, 사유 기록
본문이 너무 짧음   → 저장 안 함, 사유 기록
전부 건너뜀       → exit 3 (조용한 성공 금지)
```

**파서가 없으면 성공으로 기록하지 않는다.** §1.2 가 이 규칙의 부재로 생겼다.
구체적으로 두 가지를 금지한다.

- 페이지 원문(`html_text`)을 파싱 결과 자리에 저장하는 것
- 카테고리별 파서가 없는데 원문 하나를 여러 카테고리에 복사해 넣는 것

파서가 없으면 상태는 `succeeded` 가 아니라 `parser_missing` 이다. 수집이
안 되는 것보다 **안 되는 걸 모르는 것**이 나쁘다.

**다만 부분 실패를 실패로 단정하지는 않는다.** 오탐이 나면 정상 수집까지
막힌다. 수치를 남겨 사람이 판단하게 한다.

### 4.5 페이지 전이 — 같은 루프를 다시 돈다

다음 페이지가 나오면 **①부터 다시** 한다. 이전 페이지의 셀렉터를 그대로 쓰지
않는다.

| 신호 | 의미 |
|---|---|
| URL 변경 | 명백한 전이 — 재관측 필수 |
| 조작 요소 집합이 크게 달라짐 | SPA 내 화면 전환 — 재관측 필수 |
| 요소 수가 같고 셀렉터도 동일 | 같은 화면 — 재관측 생략 가능 |

SPA 는 URL 이 안 바뀌어도 화면이 갈린다. URL 만 보면 안 되고 **요소 집합을
지문처럼 비교**해야 한다.

관측 1회(6~15초)가 시행착오 한 번(6~25초)보다 싸다. **의심스러우면 재관측한다**
가 기본값이어야 한다.

## 5. 세션 수명 관리

로그인이 자동화의 관문이라면, 세션 유지가 **작업 길이의 상한**을 정한다.
§2의 유형 C(1,743건)가 여기에 해당한다.

### 5.1 무조작 타임아웃은 활동으로 갱신된다

국내 은행의 10분 제약은 *무조작* 기준이다. 조작이 이어지면 갱신된다. 따라서
"10분 안에 전부 끝내라"가 아니라 **"10분 이상 놀지 마라"** 가 맞는 제약이다.

```
잘못된 전제   로그인 → 10분 안에 급하게 완료
맞는 전제     로그인 → 활동을 이어가며 장시간 운용
```

계좌별·기간별 조회를 연달아 돌리면 그 작업 자체가 갱신 신호가 된다.

### 5.2 그래도 확인해야 하는 세 가지

| 항목 | 왜 |
|---|---|
| **절대 세션 한도** | 활동과 무관하게 30~60분에서 끊는 곳이 있다. 갱신이 안 되므로 중간 재로그인 지점을 설계에 넣어야 한다 |
| **연장 확인 팝업** | "세션을 연장하시겠습니까?" 가 뜨고 클릭을 요구한다. 셀렉터만 알면 자동으로 누를 수 있으므로 오히려 유리하다 |
| **keep-alive 탐지** | 의미 없는 요청을 주기적으로 찍으면 자동화로 잡힐 수 있다. 실제 조회 작업 자체를 간격으로 삼는다 |

### 5.3 헤드리스 강등을 차단한다 — 구현 완료

브라우저 브릿지의 폴백 사슬이 이렇다.

```
pc_bridge → headless → http_api → container_health
```

실제로 `PC_AGENT_OFFLINE` 상태의 세션이 `kind=headless` 로 남아 있었다. 문제는
**헤드리스가 봇 차단을 통과하지 못한다**는 점이다. GenSpark 는 헤드리스에 로그인
화면조차 주지 않고 검증 페이지만 준다.

즉 PC Agent 가 꺼지면 자동화가 멈추는 게 아니라 **쓸모없는 결과를 계속
만들어낸다.** 4월 수집기 고장과 같은 형태다.

→ `PcAgentUnavailable` + `_assert_pc_agent()` (`3d8dc648`). PC Agent 가 필요한
  작업은 `require_pc_agent=True` 를 명시하고, 헤드리스로 강등되면 실행하지 않고
  끊는다.

### 5.4 흐름

```
① 사람이 로그인 (보안키보드가 있으면 불가피)
② 로그인 완료 감지 → 자동 트리거
③ 작업 수행 — 조회를 연달아 돌려 세션을 살린다
④ 연장 팝업이 뜨면 눌러 연장
⑤ 로그인 화면이 나오면 즉시 중단, 저장하지 않음
```

④가 장기 운용의 핵심이다. ⑤는 §4.4 의 검증 원칙과 같다 — 세션이 끊긴 뒤의
화면을 결과로 저장하면 4월의 2,406건이 반복된다.

## 6. 운영 요건

기능이 아니라 **운영이 성립하기 위한 조건**이다. 없으면 오늘 같은 상황(잘못
돌고 있는 걸 알아도 멈출 수 없음)이 반복된다.

### 6.1 즉시 정지 스위치 — 구현 완료

오늘 배달 수집을 멈추려 했는데 **끄는 자리가 어디에도 없었다.** 코드에
스케줄만 있고 켜고 끄는 스위치가 없어, 멈추려면 배포(약 20분)가 필요했다.

수집이 잘못 돌고 있다는 걸 알았을 때 **즉시 멈출 수 없다**는 게 결함이다.
잘못된 수집이 계속 돌면 쓰레기 데이터가 쌓이고, 그 사이 중복 차단으로 다른
작업까지 막힌다(§1.4).

→ `app/services/collection_pause.py` (`4fa05539`). DB 한 줄로 제어한다.
  앱 재시작도 배포도 필요 없다.

```
카테고리  ops
키        collection_paused
값        {"delivery": true, "reason": "...", "paused_at": "...", "by": "..."}
```

원칙 둘.

- **읽기 실패는 "멈추지 않음"** 으로 처리한다. 스위치 조회가 안 된다고 정상
  수집을 막으면 DB 일시 장애가 곧 수집 중단이 된다
- **이유를 반드시 남긴다.** 없으면 다음 사람이 켜도 되는지 판단할 수 없다.
  멈춘 채로 잊히는 것이 계속 도는 것만큼 나쁘다

현재 상태: 2026-09-13 18:20 배달 수집 정지 중. 적용 후 시도 0건 확인.

### 6.2 사람 개입 절차 — 캡차·추가 인증

`DDANGYO_NUMERIC_CAPTCHA_REQUIRED` 137건, `PORTAL_AUTH_CHALLENGE` 153건.
자동화가 넘을 수 없는 지점이고, **넘으려 시도해서도 안 된다**(봇 탐지 우회는
하지 않는다).

필요한 것은 우회가 아니라 **규약**이다.

| 단계 | 내용 |
|---|---|
| 인지 | 캡차·인증 화면을 셀렉터/문구로 판별한다 |
| 보류 | 실패로 끝내지 않는다 — 세션을 버리면 로그인부터 다시다 |
| 통지 | 사람에게 알린다. 어느 사이트, 어느 계정, 무엇을 요구하는지 |
| 대기 | 사람이 처리할 때까지 대기(상한 있음). 그동안 세션을 살린다(§5.1) |
| 재개 | 처리 후 중단 지점부터 이어간다 |
| 만료 | 상한 초과 시 `action_required` 로 기록. **성공으로 기록하지 않는다** |

`resume_token` / `challenge_timeout_seconds` 가 payload 에 이미 있다(1,666건).
기구는 있고 절차가 문서화되지 않았다.

### 6.3 금융 재시도 금지 — 구현 완료

일반 사이트는 재시도가 싸다. 은행은 **로그인 실패가 누적되면 계정이 잠긴다.**
잠기면 자동화가 멈추는 정도가 아니라 사람이 영업점·ARS 로 풀어야 한다.

→ `app/services/financial_retry_policy.py` (`3d8dc648`).

```
절대 금지   auth_failed · account_locked · cert_required · extra_auth_required
허용        network · pc_agent_unavailable · page_not_ready
unknown     재시도 안 함
```

`unknown` 을 금지하는 게 핵심이다. 모르는 실패를 은행에 다시 던지는 건 계정
잠금을 감수하는 일이다. 잘못 재시도해 잠그는 쪽이, 한 번 더 안 해서 거르는
쪽보다 훨씬 비싸다.

### 6.4 감사 기록 — 구현 완료

`authenticated_collector_audit_log` 에 설정 등록 5건만 있고 **실행 기록이 하나도
없었다.** 무엇을·언제·어느 계정으로 조회했는지 남지 않으면 금융 자동화로
성립하지 않는다.

→ `app/services/financial_audit.py` (`3d8dc648`). 두 원칙.

- **자격증명은 남기지 않는다.** 계정은 마스킹만(`moo***@naver.com`).
  password/secret/token 키는 기록 직전에 제거한다
- **실패도 남긴다.** 성공만 기록하면 조용한 실패가 감사에서도 사라진다

### 6.5 동시 실행 금지

`yeoljeong_bank_collector_harness.py` 에 `financial_exclusive` 레인이 있다.
브라우저 세션이 하나뿐이므로 동시 실행은 서로의 화면을 망가뜨린다.

§1.4 의 중복 실행과 다른 문제다. 저쪽은 *같은 작업*이 겹친 것이고 이쪽은
*다른 작업*이 한 브라우저를 다툰다. 둘 다 필요하다.

중복 실행 대책은 세 단계다.

1. **잠금을 서비스 단위로 본다.** 지금은 job id 단위(`max_instances=1`)라 서로
   다른 job 이 같은 서비스를 동시에 노리는 것을 못 막는다(§1.4)
2. **선행 회차의 실제 종료를 확인한 뒤** 다음 회차를 낸다. 아직 돌고 있으면
   건너뛰고 **건너뛴 사실을 기록**한다. 지금은 뒤늦게 실행돼
   `ALREADY_RUNNING` 으로 죽으므로, 로그만 보면 "실패"와 구분되지 않는다
3. **catchup 주기를 회차 소요에 맞춘다.** 10분 간격 job 이 10분 넘게 걸리는
   작업을 쫓는 구조 자체가 중복을 만든다

### 6.6 자격증명 취급

- Vault 에서 읽어 **프로세스 안에서만** 쓴다
- argv 에 싣지 않는다(프로세스 목록 노출) — stdin 으로만 전달
- 로그·stdout 에 출력하지 않는다. 성공/실패만 남긴다
- 인증 화면 캡처는 최소화한다(화면에 값이 찍힌다)

## 7. 두 개의 레인 — 섞지 않는다

같은 "웹 자동화"로 묶이지만 비용 구조가 완전히 다르다.

| | **원격 레인** | **자체 레인** |
|---|---|---|
| 대상 | 배달·은행·GenSpark (남의 사이트) | 우리 프론트 (`aads.newtalk.kr`) |
| 경로 | 서버 → WS → PC Agent → CDP → 크롬 | 서버에서 헤드리스 직접 |
| 왕복 | 6~25초 | 수십 ms |
| 봇 차단 | 통과 못 함 → PC Agent 필수 | 해당 없음 |
| 로그인 | 사람 개입 필요 | storage_state 로 자동 |
| 제약 | CEO PC 가 켜져 있어야 함 | 없음 |

**자체 레인에는 이 PRD 의 왕복 최적화가 필요 없다.** 관측을 몇 번 하든 싸다.
대신 원격 레인이 못 하는 것을 할 수 있다 — 매 페이지 전수 검사, 회귀 비교,
CI 연동.

자체 레인에서 잡을 수 있는 것(오늘 React #31 같은 사례).

- 런타임 오류 — React 최소화 오류(#31 객체 렌더, #418 hydration), 콘솔 예외
- 실패한 요청 — 4xx/5xx, 타임아웃, CORS
- 에러 바운더리 발동 — "오류가 발생했습니다" 화면 자체
- 응답 크기 — 렌더 실패를 유발하는 과대 payload
- 숨은/겹친 요소 — 클릭해도 반응 없는 UI

자체 레인이 못 하는 것: **디자인 품질 판단.** 정렬·여백·색이 "이상한지"는
시각 QA 감리의 몫이고 별개 과제다.

→ 별도 과제: 프론트 진단기(미착수). 관측기(§4.1)의 셀렉터 수집을 재사용하되
  브릿지 대신 로컬 헤드리스로 돈다.

| 4 검증 가드 | 거부 규칙 + 감사 기록 적용 |

| 항목 | 내용 | 우선 |

| **Shadow DOM** | 관측기가 수집하지 못한다 | 낮 |

## 12. 한계

- **신뢰 이벤트를 요구하는 컴포넌트는 자동화할 수 없다.** GenSpark 모델
  드롭다운이 이 경우로 의심된다. §4.2 의 기록으로 판정할 수 있지만, 판정이
  "불가"로 나오면 우회가 아니라 **사람이 한 번 누르는 절차**로 설계한다
- **봇 탐지 우회는 하지 않는다.** 핑거프린트 위조·스텔스 플러그인은 범위 밖이다.
  차단되면 사람 개입(§6.2)으로 처리한다
- **왕복 비용 자체는 줄지 않는다.** 이 설계는 왕복 *횟수*를 줄이는 것이지 한 번의
  6~25초를 줄이지 못한다. PC Agent 통신 구간 최적화는 별도 과제다
- **원격 레인은 CEO PC 에 의존한다.** PC 가 꺼지면 자동화가 멈춘다. §5.3 은
  멈추는 걸 막는 게 아니라 **멈춘 걸 성공으로 기록하지 않게** 하는 장치다
