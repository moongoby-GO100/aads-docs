# 배포 신뢰성 PRD — 실패 원인 해소와 자동 재시작

작성: 2026-09-13 · 개정: 2026-09-13(D1·D2·D4·D5·D6·D7·D8 적용 반영)
대상: `aads-server` 블루/그린 배포 파이프라인

## 1. 문제

2026-09-13 하루 배포 56건의 결과다.

| 결과 | 건수 | 비율 |
|---|---|---|
| success | 13 | 23% |
| **failed** | **20** | 36% |
| **blocked** | **11** | 20% |
| superseded(정상 흡수) | 11 | 20% |
| 진행 중 | 1 | — |

**성공률 23%**다. 같은 릴리스를 5번 시도해 전부 실패한 경우도 있다(`5881b667`:
blocked,failed,blocked,failed,blocked).

이것이 운영에 미치는 영향은 배포 실패 자체가 아니다.

- **커밋이 라이브에 닿지 않는다.** 어제 `a49eee32`(OAuth 자동갱신)가 커밋만 되고
  배포되지 않아, 오늘 토큰 만료로 채팅이 두 번(21:40, 23:49) 멈췄다.
- **"조치 완료" 보고와 실제 반영 사이에 간극이 생긴다.** 오늘 최소 3회 확인됐다.
- **러너 작업이 끊긴다.** 배포마다 컨테이너가 교체되며, 24시간 러너 실패 38건 중
  13건이 "서버 재시작으로 중단"이다.

## 3. 현재 구현과 그 한계

### 3.1 이미 있는 것

**`scripts/deploy_autoheal.sh`** (커밋 `8b5e9a12`, 21KB)

- `classify_deploy_failure()` — disk_full / dirty_worktree / stale_heartbeat /
  lock_wait_timeout 분류
- `autoheal_policy()` — 원인별 retry / manual 결정
- 컷오버 이후 단계(`autoheal_phase_is_post_switch`)는 재시도하지 않는다.
  이미 트래픽이 넘어간 뒤라 재시도가 더 위험하기 때문이다. 옳은 판단이다.
- 재시도 상한 `AADS_DEPLOY_AUTOHEAL_MAX_ATTEMPTS` 기본 **1회**

**`supersede_older_queued_deploy_requests()`** (`deploy.sh:540`)

- 배포 시작 시 큐에 대기 중인 **다른 SHA** 요청을 `superseded`로 닫는다.
- git 커밋은 누적이므로 나중 SHA가 앞선 커밋을 포함한다. 대기 요청을 버려도
  내용은 잃지 않는다. 오늘 11건이 이렇게 흡수됐다.

### 3.2 한계

**(a) autoheal 은 작동한다. 다만 절반을 `manual` 로 넘긴다.**

처음에는 "31건 중 1건만 작동"으로 판단했으나 틀렸다. 그 수치는 `error_summary`
에 'autoheal' 문자열이 들어간 DB 건수였고, **실제 동작은 로그에만 남는다.**
DB 만 보고 내린 판단이었다.

로그 기준 실제 분류는 18건이다.

| 분류 | 건수 | 처리 |
|---|---|---|
| `disk_full` | 4 | retry |
| `unexpected_exit` | 4 | **manual** |
| `other` | 4 | **manual** |
| `standby_sync_fail` | 2 | 컷오버 후라 재시도 안 함 |
| `signal_interrupt` | 2 | — |
| `dirty_worktree` | 2 | ✅ **재개 성공** |

성공 사례가 로그에 남아 있다.

```
[autoheal] 재개 큐 등록: deploy_run_id=378, release=662d26c2faef
[autoheal] ✅ 자가치유 재개 기동 완료:
           cause=dirty_worktree, remediation=route_clean_worktree
```

문제는 **`manual` 8건**이다. `unexpected error exit=` 라는 한 통에 성격이 다른
실패가 섞여 들어가 전부 사람 손을 기다린다.

그리고 그 메시지가 전부 `line=1` 이었다. 어느 줄에서 죽었는지 없이 문자열만 보고
분류해야 했으니 한 통에 섞인 것이 당연하다. 뒤에 이것이 `set -E` 누락 때문임을
확인했다(D7).

**(b) 같은 SHA 중복 요청을 흡수하지 못한다.** → D2 에서 해소.

```sql
WHERE status='queued' AND release_sha IS DISTINCT FROM '<시작 SHA>'
```

`IS DISTINCT FROM` 때문에 **같은 SHA** 는 흡수 대상에서 빠진다. 또 `queued` 만
보므로 이미 `running` 인 중복은 건드리지 않는다. 오늘 #348/#349, #379/#380 이
같은 커밋으로 동시에 돌았다.

**(c) 실패가 사후에만 처리된다.** disk_full 8건은 빌드 직전까지 갔다가 막혔다.
preflight 에서 정리하면 애초에 실패하지 않는다. → 확인해 보니 이 순서는 이미
구현돼 있었다(D1). `reject_duplicate_live_release` → `prune_old_release_images`
→ `require_build_disk_free` 순으로 돈다. #351 은 정리를 하고도 467MB 가 모자라
막힌 것이므로 판정 자체는 옳았다. 한계는 순서가 아니라 **정리 폭**에 있다.

**(d) 재시도 상한이 1회다.** → D3 보류. 실제로 상한에 걸려 실패한 사례가 없다. 디스크를 정리하고 재시도했는데 그사이 다른 배포가
디스크를 다시 쓰면 두 번째 기회가 없다.

## 4. 설계

### 4.1 원칙

1. **예방이 회복보다 싸다.** 실패한 뒤 고치는 것보다 시작 전에 조건을 맞춘다.
2. **컷오버 이후에는 재시도하지 않는다.** 트래픽이 넘어간 뒤의 재시도는
   되돌리기 어렵다. 현재 구현의 이 판단을 유지한다.
3. **중복은 흡수하되 내용은 잃지 않는다.** git 커밋이 누적이라는 성질에 기댄다.
4. **실패는 반드시 원인이 남아야 한다.** 원인 없는 실패는 고칠 수 없다.

### 4.2 변경 항목

| # | 항목 | 해소 대상 | 상태 |
|---|---|---|---|
| D1 | preflight 에서 디스크 정리 후 재확인 | disk_full 8건 | ✅ 이미 적용돼 있었음 |
| D2 | 같은 SHA 중복 요청 흡수 | 중복 빌드 | ✅ 적용 |
| D3 | autoheal 재시도 상한 1 → 2 | 정리 후 재경합 | ⏸ 보류 |
| D4 | autoheal 미작동 원인 규명 | — | ✅ 완료(오진 정정) |
| D5 | 스크립트 오류 3건 수정 | 코드 결함 | ✅ 타 세션 `8b5e9a12` |
| D6 | `manual` 8건의 분류 세분화 | 자동 교정 불가 8건 | ✅ 적용 |
| **D7** | **ERR 트랩 줄번호 유실(`line=1`)** | 원인 미상 실패 전부 | ✅ 적용 |
| **D8** | **standby 드레인 보류를 실패로 집계** | failed 3건 | ✅ 적용 |

**D1** — `prune_old_release_images` 와 디스크 가드는 이미 있다. preflight 에서
정리를 먼저 돌리고 그 결과로 판정하면 disk_full 은 대부분 사라진다.
(오늘 #351 이 467MB 부족으로 막혔는데, 정리 후 27GB 가 확보됐다.)

**D2** — supersede 조건에서 `IS DISTINCT FROM` 을 제거하고, 같은 SHA 의 더 오래된
`queued` 요청도 닫는다. 단 `running` 은 건드리지 않는다 — 진행 중인 배포를
큐 정리가 중단시키면 안 된다.

**D4 (완료)** — 조사 결과 autoheal 은 정상 작동한다. 호출 경로도 끊기지 않았다.
`deploy.sh:1442` 의 EXIT 트랩에서 호출되고, 소스 로드도 정상이다
("자가치유 없이 진행" 로그가 한 번도 찍히지 않았다).

**D6 (적용 완료, 커밋 `59ea54f0`)** — `manual` 8건의 원본 메시지를 보면 성격이
다른 둘이 한 통에 있었다.

```
unexpected error exit=1 line=1: docker compose ... --force-recreate "$NEW_CONTAINER"
unknown mode: status | autoheal escalated
```

앞은 컨테이너 재생성이 자원 경합으로 실패한 것이라 재시도할 값이 있고, 뒤는
없는 모드로 호출한 것이라 재시도해도 같은 결과다. 분류를 나눴다.

- `container_recreate_fail` — 컷오버 이전이면 retry, 이후면 manual
- `invalid_mode` — manual (재시도 무의미)

실제 메시지 7종으로 검증했다. `unknown mode` 자체는 다른 세션이 `8b5e9a12` 로
이미 고쳤다(`deploy.sh:17` 에 경위 기록, 단위 테스트 포함).

**D7 (적용 완료)** — `line=1` 의 원인은 stderr 유실이 아니라 `set -E`(errtrace)
누락이었다. ERR 트랩은 기본적으로 함수와 서브셸에 상속되지 않아, 함수 안에서
실패해도 트랩이 호출 지점에서 발동한다. 실측으로 확인했다.

```
set -E 없음 → line=8 (호출 지점만)
set -E 있음 → line=6 (실제 실패 줄이 먼저)
```

`set -euo pipefail` → `set -Eeuo pipefail`. `|| true` 로 감싼 실패는 `set -E` 가
있어도 트랩을 부르지 않아(발동 0회) 중복 기록 위험은 없다.

이것이 **자가치유가 원인을 분류하지 못한 근본 이유**다. 줄 번호가 없으니 메시지
문자열만으로 판단해야 했고, 그래서 `manual` 로 빠졌다. D6 이 증상을, D7 이 원인을
다룬다.

**D8 (적용 완료)** — standby 동기화는 대기 슬롯을 같은 이미지로 맞추는 마지막
단계다. 그 슬롯에 진행 중인 대화가 남아 있으면 드레인을 기다리고, 600초 안에
비지 않으면 포기한다. 진행 중인 대화를 끊지 않으려는 의도된 동작이다.

그런데 이때 **배포 전체를 `failed` 로 기록**했다. 컷오버는 이미 성공해 새 릴리스가
트래픽을 받고 있는데도 그렇다. 성공률이 실제보다 낮게 보이고 자가치유가 헛된
재시도를 걸었다.

드레인 타임아웃(반환 2)과 진짜 동기화 실패(반환 1)를 구분하고, 전자는 스키마에
이미 있던 `success_partial` 로 닫는다. 배포는 중단하지 않고 검증을 계속한다.

**대기 슬롯이 구버전이라는 사실은 성공과 구분해 남긴다.** 폴백이 일어나면 그
릴리스가 빠진 이미지로 돌아가기 때문이다. 숨기면 안 되는 정보다.

### 4.3 결과 상태 모델 (D8 이후)

배포 결과를 세 가지로 나눈다. 이전에는 성공/실패 둘뿐이라 "라이브에는 반영됐지만
대기 슬롯이 안 맞은" 상태를 표현할 자리가 없었다.

| 상태 | 뜻 | 라이브 | 대기 슬롯 | 자가치유 |
|---|---|---|---|---|
| `success` | 전 단계 완료 | 신규 | 신규 | — |
| `success_partial` | 컷오버 완료, 동기화 보류 | 신규 | **구버전** | 재시도 안 함 |
| `failed` | 컷오버 전 중단 또는 동기화 실패 | 기존 유지 | 기존 | 정책에 따름 |

`success_partial` 은 새로 만든 값이 아니다. `deploy_runs.status` 의 CHECK 제약에
이미 있었고 쓰이지 않았을 뿐이다. 마이그레이션이 필요 없다.

구현은 동기화 함수의 반환값을 셋으로 나누는 것으로 끝난다.

| 반환 | 뜻 | 처리 |
|---|---|---|
| 0 | 동기화 완료 | `standby_same_digest_sync` = success |
| 2 | 드레인 타임아웃(진행 중인 대화 있음) | phase = skipped, 배포 계속, 최종 `success_partial` |
| 1 | 동기화 자체 실패 | `failed` 기록 후 중단 |

호출부는 `|| _standby_rc=$?` 로 받아 세 갈래로 분기한다. `set -e` 아래에서
0 이 아닌 반환을 그대로 두면 스크립트가 죽으므로 `||` 로 받는 것이 필수다.

**자가치유가 헛돌지 않는 이유.** `success_partial` 로 끝난 배포는 exit 0 이다.
EXIT 트랩의 `deploy_autoheal_on_exit` 는 0 을 보고 즉시 반환하므로 재시도 경로에
들어가지 않는다. 별도 예외 처리가 필요 없다.

### 4.4 실패 진단 경로 (D7 이후)

실패 메시지가 자가치유 분류로 이어지는 경로다. 여기 어디가 끊기면 전부 `manual`
로 떨어진다.

```
셸 실패
  └─ ERR 트랩 (set -E 로 함수·서브셸까지 상속)
       └─ "unexpected error exit=<코드> line=<줄> : <명령>"
            └─ classify_deploy_failure()  ← 이 문자열로 판정
                 └─ autoheal_policy()  → retry | manual
```

`set -E` 가 없으면 `line` 이 호출 지점(또는 1)이 되어 3단계에서 쓸 정보가
사라진다. 분류가 문자열에만 의존하는 구조이므로, **트랩이 정확한 줄을 남기는 것이
분류 정확도의 상한**이다.

### 4.5 하지 않을 것

- **배포 시 러너 드레인.** 조사 결과 재시작 중단 15건 중 14건(93%)이 이미 자동
  재실행된다. 재실행분이 다시 실패하는 주된 원인은 배포가 아니라
  `review_infra_failed`(6건)다. 드레인을 넣어도 개선 폭이 작고, 러너 작업이 최대
  20시간이라 배포가 무기한 밀린다.
- **컷오버 이후 자동 재시도.** 4.1-2 참조.

## 5. 검증 기준

| 지표 | 적용 전 | 목표 |
|---|---|---|
| 배포 성공률 | 23% | 70% 이상 |
| disk_full 실패 | 8건/일 | 0 |
| 같은 SHA 중복 빌드 | 3회 이상/일 | 0 |
| `line=1` 실패 | 전건 | 0 |
| `standby_sync` 로 인한 failed | 3건/일 | 0 (→ `success_partial`) |

측정은 `deploy_runs` 24시간 집계로 한다. 수치가 아니라 **"커밋이 라이브에 닿기까지
걸린 시간"** 이 실제 목적이므로, 성공률과 함께 커밋→반영 지연도 본다.

**성공률 계산에서 주의할 점 하나.** D8 이후 standby 드레인 보류는 `failed` 가
아니라 `success_partial` 로 닫힌다. 성공률이 올라가는 것은 맞지만 그중 일부는
고쳐서가 아니라 **집계 분류가 바뀌어서**다. 두 기준을 같이 봐야 한다.

- `success` 만 — 컷오버와 대기 슬롯 동기화가 모두 끝난 것
- `success + success_partial` — 라이브에 반영된 것

목표 70% 는 후자 기준이다. 전자는 진행 중인 대화 수에 좌우되므로 코드 품질
지표로 쓰기 어렵다.

## 6. 순서

D1~D8 중 D3 을 뺀 전부가 적용됐다. 적용 순서와 근거는 다음과 같았다.

1. **D4 조사** — 나머지 판단의 전제였다. 결과는 오진 정정이었다.
2. **D6** — 증상(분류가 한 통에 섞임)을 나눴다.
3. **D7** — 원인(`set -E` 누락)을 고쳤다. D6 만으로는 다음 새 실패에서 같은 일이
   반복된다.
4. **D2** — 같은 SHA 중복 흡수.
5. **D8** — standby 보류를 실패에서 분리.
6. **D3** — 보류. 재시도 상한(1회)에 걸려 실패한 사례가 없다. D7 로 분류가
   정확해진 뒤 재측정해서 결정한다.

모두 실측 검증을 거쳤다. D7 은 `set -E` 유무에 따른 줄번호 차이를, D8 은 세 반환
경로(0/2/1)의 분기를, D2 는 `running` 행이 보존되는지를 각각 확인했다.

## 7. 미결

작성 시점의 미결 두 건은 모두 닫혔다. autoheal 호출 여부는 D4 에서 규명됐고
(호출된다), `standby_sync` 집계는 D8 에서 `success_partial` 로 정리됐다.
남은 것은 다음과 같다.

- **D3 재시도 상한.** D7 로 분류가 정확해진 뒤 24시간을 재측정해서 결정한다.
  지금 올리면 근거 없이 재시도만 늘린다.
- **대기 슬롯이 구버전으로 남는 시간.** `success_partial` 로 닫힌 배포는 폴백이
  일어나면 이전 이미지로 돌아간다. 드레인이 끝난 뒤 뒤늦게 동기화하는 경로가
  없다. 지금은 다음 배포가 대신 맞춰 준다.
- **`review_infra_failed`.** 배포가 아니라 러너 쪽 문제지만, 자동 재실행된 러너
  작업이 다시 실패하는 최대 원인(12건 중 6건)이다. 별도 과제.
- **preflight 정리 폭.** #351 은 정리를 하고도 467MB 가 모자랐다. 정리 대상에
  무엇을 더 넣을지는 디스크 가드와 같이 봐야 한다.
