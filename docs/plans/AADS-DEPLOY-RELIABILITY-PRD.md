# 배포 신뢰성 PRD — 실패 원인 해소와 자동 재시작

작성: 2026-09-13 · 대상: `aads-server` 블루/그린 배포 파이프라인

## 1. 문제

2026-09-13 하루 배포 56건의 결과다.

| 결과 | 건수 | 비율 |
|---|---|---|
| success | 13 | 23% |
| **failed** | **20** | 36% |
| **blocked** | **11** | 20% |
| superseded(정상 흡수) | 11 | 20% |
| 진행 중 | 1 | — |

**성공률 23%**다. 같은 릴리스를 5번 시도해 전부 실패한 경우도 있다(`5881b667`:
blocked,failed,blocked,failed,blocked).

이것이 운영에 미치는 영향은 배포 실패 자체가 아니다.

- **커밋이 라이브에 닿지 않는다.** 어제 `a49eee32`(OAuth 자동갱신)가 커밋만 되고
  배포되지 않아, 오늘 토큰 만료로 채팅이 두 번(21:40, 23:49) 멈췄다.
- **"조치 완료" 보고와 실제 반영 사이에 간극이 생긴다.** 오늘 최소 3회 확인됐다.
- **러너 작업이 끊긴다.** 배포마다 컨테이너가 교체되며, 24시간 러너 실패 38건 중
  13건이 "서버 재시작으로 중단"이다.

## 2. 실패 원인 (실측)

24시간 failed/blocked 31건의 분류다.

| 원인 | 건수 | 성격 |
|---|---|---|
| `disk_full` | 8 | 자동 회복 가능 |
| `stale_heartbeat` | 6 | 자동 회복 가능 |
| `dirty_worktree` | 5 | 자동 회복 가능(클린 워크트리 재시도) |
| `interrupted_TERM` | 3 | 자동 회복 가능 |
| `standby_sync` | 3 | 서비스 영향 없음(컷오버 후 단계) |
| 스크립트 오류 | 3 | 코드 수정 필요 |
| `unknown mode` | 1 | 코드 수정 필요 |

**26건(84%)이 원인이 특정된 반복 실패**다. 새로운 문제가 아니라 같은 원인이
매번 반복된다.

## 3. 현재 구현과 그 한계

### 3.1 이미 있는 것

**`scripts/deploy_autoheal.sh`** (커밋 `8b5e9a12`, 21KB)

- `classify_deploy_failure()` — disk_full / dirty_worktree / stale_heartbeat /
  lock_wait_timeout 분류
- `autoheal_policy()` — 원인별 retry / manual 결정
- 컷오버 이후 단계(`autoheal_phase_is_post_switch`)는 재시도하지 않는다.
  이미 트래픽이 넘어간 뒤라 재시도가 더 위험하기 때문이다. 옳은 판단이다.
- 재시도 상한 `AADS_DEPLOY_AUTOHEAL_MAX_ATTEMPTS` 기본 **1회**

**`supersede_older_queued_deploy_requests()`** (`deploy.sh:540`)

- 배포 시작 시 큐에 대기 중인 **다른 SHA** 요청을 `superseded`로 닫는다.
- git 커밋은 누적이므로 나중 SHA가 앞선 커밋을 포함한다. 대기 요청을 버려도
  내용은 잃지 않는다. 오늘 11건이 이렇게 흡수됐다.

### 3.2 한계

**(a) autoheal 이 거의 작동하지 않았다.** 24시간 실패 31건 중 autoheal 이
언급된 배포는 **1건**이다. 분류 로직은 있으나 실제 회복으로 이어지지 않았다.

**(b) 같은 SHA 중복 요청을 흡수하지 못한다.**

```sql
WHERE status='queued' AND release_sha IS DISTINCT FROM '<시작 SHA>'
```

`IS DISTINCT FROM` 때문에 **같은 SHA** 는 흡수 대상에서 빠진다. 또 `queued` 만
보므로 이미 `running` 인 중복은 건드리지 않는다. 오늘 #348/#349, #379/#380 이
같은 커밋으로 동시에 돌았다.

**(c) 실패가 사후에만 처리된다.** disk_full 8건은 빌드 직전까지 갔다가 막혔다.
preflight 에서 정리하면 애초에 실패하지 않는다.

**(d) 재시도 상한이 1회다.** 디스크를 정리하고 재시도했는데 그사이 다른 배포가
디스크를 다시 쓰면 두 번째 기회가 없다.

## 4. 설계

### 4.1 원칙

1. **예방이 회복보다 싸다.** 실패한 뒤 고치는 것보다 시작 전에 조건을 맞춘다.
2. **컷오버 이후에는 재시도하지 않는다.** 트래픽이 넘어간 뒤의 재시도는
   되돌리기 어렵다. 현재 구현의 이 판단을 유지한다.
3. **중복은 흡수하되 내용은 잃지 않는다.** git 커밋이 누적이라는 성질에 기댄다.
4. **실패는 반드시 원인이 남아야 한다.** 원인 없는 실패는 고칠 수 없다.

### 4.2 변경 항목

| # | 항목 | 해소 대상 | 위험 |
|---|---|---|---|
| D1 | preflight 에서 디스크 정리 후 재확인 | disk_full 8건 | 낮음 |
| D2 | 같은 SHA 중복 요청 흡수 | 중복 빌드 | 낮음 |
| D3 | autoheal 재시도 상한 1 → 2 | 정리 후 재경합 | 낮음 |
| D4 | autoheal 미작동 원인 규명 | 31건 중 30건 미처리 | 조사 필요 |
| D5 | 스크립트 오류 3건 수정 | 코드 결함 | 낮음 |

**D1** — `prune_old_release_images` 와 디스크 가드는 이미 있다. preflight 에서
정리를 먼저 돌리고 그 결과로 판정하면 disk_full 은 대부분 사라진다.
(오늘 #351 이 467MB 부족으로 막혔는데, 정리 후 27GB 가 확보됐다.)

**D2** — supersede 조건에서 `IS DISTINCT FROM` 을 제거하고, 같은 SHA 의 더 오래된
`queued` 요청도 닫는다. 단 `running` 은 건드리지 않는다 — 진행 중인 배포를
큐 정리가 중단시키면 안 된다.

**D4** — 이것이 가장 중요하다. autoheal 이 구현돼 있는데 31건 중 1건에서만
언급됐다는 것은, 분류나 호출 경로 어딘가가 끊겨 있다는 뜻이다. 먼저 **왜 호출되지
않았는지**를 확인해야 하며, 그 전에 상한이나 정책을 손대는 것은 의미가 없다.

### 4.3 하지 않을 것

- **배포 시 러너 드레인.** 조사 결과 재시작 중단 15건 중 14건(93%)이 이미 자동
  재실행된다. 재실행분이 다시 실패하는 주된 원인은 배포가 아니라
  `review_infra_failed`(6건)다. 드레인을 넣어도 개선 폭이 작고, 러너 작업이 최대
  20시간이라 배포가 무기한 밀린다.
- **컷오버 이후 자동 재시도.** 4.1-2 참조.

## 5. 검증 기준

| 지표 | 현재 | 목표 |
|---|---|---|
| 배포 성공률 | 23% | 70% 이상 |
| disk_full 실패 | 8건/일 | 0 |
| 같은 SHA 중복 빌드 | 3회 이상/일 | 0 |
| 원인 미기록 실패 | 3건 | 0 |

측정은 `deploy_runs` 24시간 집계로 한다. 수치가 아니라 **"커밋이 라이브에 닿기까지
걸린 시간"** 이 실제 목적이므로, 성공률과 함께 커밋→반영 지연도 본다.

## 6. 순서

1. **D4 조사** — autoheal 미작동 원인. 나머지 판단의 전제다.
2. **D1 + D2** — 예방. 위험이 낮고 효과가 즉시 나온다.
3. **D5** — 스크립트 오류.
4. **D3** — D4 결과를 보고 결정.

## 7. 미결

- autoheal 이 왜 호출되지 않았는지 아직 모른다. D4 조사 전에는 D3 을 확정할 수 없다.
- `standby_sync` 3건은 컷오버 완료 후라 서비스 영향이 없다. 실패로 집계할지
  별도 상태로 분리할지 판단이 필요하다. 지금은 성공률을 실제보다 낮게 보이게 한다.
