# PRD — 지시 회수: 미반영 추가지시와 잘못 보낸 지시

| 항목 | 내용 |
|---|---|
| 문서 ID | PRD-INSTRUCTION-RECOVERY-v1.0 |
| 작성일 | 2026-09-17 (KST) |
| 지시 | 대표님 — "내가 지시한 내용을 회수가 안되네 기획보고해" → "승인한다. 그리고 내가 지시를 잘못 보낸대화버블을 회수하는 방안도 보고하고 같이 반영하면 좋겠다" |
| 대상 | `aads-server` (`app/services/chat_service.py`, `app/routers/chat.py`, `app/main.py`), `aads-dashboard` (`src/app/chat/page.tsx`) |
| 오류 사전 | `chat.interrupt_never_recovered`, `chat.retract_only_hid_the_row`, `chat.runner_progress_invisible`, `chat.asyncpg_unused_parameter` |

---

## 0. 용어

| 용어 | 뜻 |
|---|---|
| **추가 지시(인터럽트)** | 답변이 진행 중일 때 덧붙이는 메시지. 새 질문이 아니라 **진행 중인 그 턴에 얹는 것** |
| **회수** | 그 지시를 꺼내 실제 답변에 반영하는 것. 코드에서는 `_collect_queued_interrupts` |
| **되회수(retract)** | 반대 방향 — 잘못 보낸 지시를 **되가져오는 것**. 이 문서 2부 |
| `queued_interrupt` | 접수됐고 아직 회수 안 됨 |
| `interrupt_needs_confirm` | 30분을 넘겨 **대표님 확인 대기** (이번에 신설) |
| `interrupt_confirmed` | 대표님이 "지금 반영" 을 누름 (이번에 신설) |
| `recovered_interrupt` | 다음 턴에 얹혀 반영됨 |
| `interrupt_expired` | 창을 넘겨 폐기 |

# 1부 — 미반영 추가지시

## 1.1 실측

```
최근 7일 추가 지시 148건
  성공  86건   (다음턴 반영 46 · 응답포함 37 · 반영중 3)
  폐기  46건   interrupt_expired
  대기  16건   queued_interrupt — 최고 23시간
  ─────────────────────────
  유실률  62/148 = 41.9%
```

대기 16건을 접두로 나누면 원인이 바로 보인다.

| 접두 | 건수 | 회수 쿼리의 `LIKE '[추가 지시%'` 에 걸리나 |
|---|---|---|
| `[CEO 승인 · 배포 지시 …]` | **4** | ❌ |
| `[CEO 지시 · 마일스톤 확정 …]` | **3** | ❌ |
| `[정정 · …]` | 2 | ❌ |
| `[추가 근거 · …]` | 2 | ❌ |
| `[추가 지시]` / `[추가 지시 · …]` | 5 | ✅ |

**11건(69%)이 회수 대상에서 빠졌고, 그중 7건이 대표님 지시다.**

## 1.2 원인 셋

### ① 접두 문자열 판정

```sql
WHERE m.content LIKE '[추가 지시%'          -- 회수
  AND COALESCE(m.intent,'') IN ('', 'queued_interrupt')
```

같은 날 오전, **밀어내기 판정**에서 똑같은 실수를 접두 → `intent` 로 고쳤다
(PRD-CHAT-TURN-RELIABILITY 3절). 그런데 **회수·만료·취소 세 쿼리에는 접두가
그대로 남아 있었다.** 같은 파일 안에서 한쪽만 고친 것이다.

접두는 계속 는다. 어제 하루에만 네 가지가 새로 나왔다.

### ② 회수 시점이 "그 세션의 다음 턴" 뿐

회수는 `_fetch_persisted_interrupts` 안에서만 일어나고, 이 함수는 그 세션에서
새 턴이 돌 때 불린다. **세션이 멈추면 아무도 돌지 않는다** — 그래서 23시간이
지나도 그대로였다.

오늘 오전 고친 버려진 실행과 구조가 같다. "정리할 주체가 없다" 가 아니라
"돌긴 도는데 그 경로로는 안 닿는다" 이고, 답도 같다 — **턴을 기다리지 않는
주체를 따로 둔다.**

### ③ 만료가 조용한 폐기

30분을 넘기면 `interrupt_expired` 로 내려가고 끝이다. 화면 배지는 있지만
되살릴 방법은 대표님이 직접 다시 보내시는 것뿐이다.

## 1.3 설계 — 3구간

`intent` 로 고르고, 경과 시간으로 나눈다.

| 경과 | 처리 | 이유 |
|---|---|---|
| **30분 이내** | 자동 회수 (지금과 같음) | 스트림이 죽어 다음 턴에 되살리는 정상 경로 |
| **30분 ~ 24시간** | `interrupt_needs_confirm` — 화면에서 **[지금 반영] / [취소]** | 자동으로 얹으면 사고, 버리면 유실 |
| **24시간 초과** | `interrupt_expired` | |

**가운데 구간이 이 설계의 핵심이다.** 어제 08:56 의 `[CEO 승인 · 배포 지시]`
를 서버가 오늘 자동 실행하면 복구가 아니라 사고다. 그렇다고 조용히 버리면
대표님 지시가 사라진다. **사람이 고르게 한다.**

`interrupt_confirmed` 는 **나이 창을 통과한다.** 30분 창은 자동 회수에만
거는 것이고, 대표님이 보고 직접 고른 것을 시간으로 다시 막을 이유가 없다.

분류는 `sweep_stale_interrupts()` 한 함수에 있고, **세션 턴과 5분 주기 배치가
같은 함수를 부른다.** 두 벌로 두면 한쪽이 낡는다.

# 2부 — 잘못 보낸 지시 회수 (retract)

## 2.1 지금 있는 것과 없는 것

| 기능 | 있나 | 하는 일 |
|---|---|---|
| `POST /interrupt/cancel` | ✅ | 대기 중 추가지시만 무름 |
| `DELETE /chat/messages/{id}` | ✅ | 메시지 + 다음 AI 응답 **하드 삭제** |
| `POST /sessions/{id}/stop` | ✅ | 스트림 중단 |

**삭제가 회수가 아닌 이유 — 확인한 것 넷.**

### ① 진행 중인 실행을 멈추지 않는다

`delete_message_and_response` 는 `chat_turn_executions` 를 **전혀 건드리지
않는다.** 메시지를 지워도 그 턴은 계속 돌며 도구를 더 실행하고 새 응답
버블을 만든다.

### ② 하드 삭제라 되돌릴 수 없다

`deleted_at` 컬럼이 **이미 있고**, 읽기 모델도 **이미** `deleted_at IS NULL`
로 거른다(`chat_read_model.py` 5곳). 그런데 **쓰는 코드가 없어 47,339행 중
0행**이었다 — 절반만 지어진 기능이다.

### ③ 모델의 기억은 DB 밖에도 있다

```
DB 이력          서버가 매 턴 렌더해 프롬프트에 넣음
CLI 릴레이 세션   /root/.claude-relay-slots/slotN/.claude/projects/*.jsonl
                 --resume 로 이어붙음. DB 를 지워도 여기는 남는다
```

**DB 만 지우면 모델은 계속 본다.** 회수 시 릴레이 세션 연결을 끊어, 다음 턴이
DB 이력만 보고 시작하게 한다. 비용은 그 한 턴의 프롬프트가 커지는 것뿐이다.

### ④ 프롬프트 이력이 `deleted_at` 을 거르지 않았다

이력 쿼리 **네 곳 모두** 거르지 않고 있었다. 이 상태로 회수하면 **화면에서만
사라지고 모델은 계속 보는** 상태가 된다. 그것은 회수가 아니다.

조건을 `_history_exclusion_sql()` **한 함수**에 넣었다. 네 곳에 흩어두면
반드시 하나를 빠뜨린다 — 1부 ①이 정확히 그 사고다.

## 2.2 설계 — 넷을 함께

`POST /chat/messages/{id}/retract`

| 단계 | 내용 |
|---|---|
| ① | 그 지시로 시작된 실행을 `cancelled` 로 중단 + `current_execution_id` 해제 |
| ② | 지시와 **그 답변만** 소프트 삭제 (`deleted_at`) |
| ③ | 딸린 대기 추가지시를 함께 무름 |
| ④ | CLI 릴레이 세션 연결을 끊어 모델 기억에서도 제거 |

**②의 범위를 좁힌 이유.** 실행 연결이 없을 때 `created_at > 원본` 으로만
잡으면 **그 뒤 모든 답변이 내려간다** — 회수가 아니라 대화 파괴다. 실행으로
묶인 것, 없으면 **바로 다음 답변 한 건**. 두 경로만 허용한다.

## 2.3 되돌릴 수 없는 것은 숨기지 않는다

최근 7일 assistant 7,301건 중 **1,165건이 도구를 호출**했다. 배포나 파일
수정이었다면 회수해도 그 일은 일어난 뒤다.

`tools_already_run` 으로 돌려주고 화면이 그대로 말한다.

```
회수했습니다 (응답 1건 중단).
다만 이미 실행된 작업이 있습니다 — Bash, Edit, deploy_remote.
이것은 되돌아가지 않습니다.
```

확인 창에서도 미리 알린다.

```
이 지시를 회수할까요?

진행 중인 응답을 멈추고, 지시와 답변을 대화에서 내립니다.
이미 실행된 작업(배포·파일 수정 등)은 되돌아가지 않습니다.
```

최근 7일 Pipeline Runner 메시지 525건 / 21개 세션 — 숨김률 100%

**일은 계속 되고 있었는데 화면만 죽어 있었다.**

## 3.2 원인 — 세 겹

| # | 지점 | 내용 |
|---|---|---|
| ① | DB 트리거 `set_chat_message_is_hidden` | 본문 마커 + `model_used` 빈값 → `is_hidden=true` |
| ② | `_visible_message_filter` | `AND is_hidden = FALSE` |
| ③ | `scripts/pipeline-runner.sh` `post_to_chat` | `chat_messages` 에 직접 INSERT 하며 **intent 를 비워 둠** |

③이 결정적이다. intent 가 없으니 `include_streaming=true` 의 허용 목록
(`runner_response`·`interrupted_partial`·`_archived_partial`)에도 걸리지 않아,
**어떤 조회 방식으로도 나오지 않았다.**

## 3.3 설계 — ①안(접힌 진행줄)

```
🤖 러너 진행 4건   작업 완료 — ✅ AI 리뷰 통과 (score=0.74)      08:33  ▸
```

누르면 펼쳐 전체를 본다.

| 판단 | 내용 |
|---|---|
| **intent 로 고른다** | 본문 문자열이 아니다. 1부 ①에서 접두 판정 때문에 대표님 지시 7건을 놓쳤다 |
| **양쪽에서 연다** | 라이브·이력 둘 다. 한쪽만 열면 "아까 있던 것이 없어졌다" 가 된다 |
| **`is_hidden` 은 true 로 남긴다** | DB 트리거가 그대로 찍어 메시지 수·목록 미리보기가 안 바뀐다. 노출은 조회 필터가 따로 연다 |
| **화면에서 접는다** | 한 작업이 시작·리뷰·완료·배포로 네댓 건을 남긴다. 안 접으면 대화가 러너 로그로 덮인다 |
| **길이 필터도 연다** | `isHiddenSystemChatMessage` 가 50자 이하 어시스턴트를 잡는데 "배포 시작"(42자)이 그 선 아래였다 |

## 3.4 과거 데이터

`intent NULL` + 러너 마커 행은 전체 기간 **1,280건 / 43개 세션**(2026-08-14~).
**최근 7일 525건만 보정한다** — 대표님이 지금 쓰시는 세션을 덮고, 이미
읽으신 지난 대화의 모양은 바꾸지 않는다.
