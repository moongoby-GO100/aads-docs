## 1. 문제 — 매 턴 76,245자

MCP 브리지가 도구 **142개**를 노출하고, CLI 는 그 스키마 전부를 매 턴 프롬프트에 싣는다.

```
도구 142개  = 76,245자 ≈ 25,000 토큰   (매 턴, 질문 내용과 무관)
```

신규 세션에 "너는 프롬프트 및 컨텍스트 엔지니어이다"(21자)를 보내도 같은 76,245자가
함께 간다. 시스템 프롬프트(36,546자)까지 더하면 **질문 1자당 배경 5,371자**다.

MCP 서버 기동 자체는 싸다 — 실측 0.3초(MCP 없이 8.27초 vs 붙여서 8.58초).
비싼 것은 기동이 아니라 **모델이 매 턴 25,000토큰을 읽는 것**이다.

---

## 2. 실측 — 도구 8개가 호출의 90%

최근 7일, 도구 호출 41,875회.

| 구간 | 누적 비중 |
|---|---|
| 상위 1개 | **57.1%** (`run_remote_command`) |
| 상위 4개 | 78.4% |
| 상위 8개 | **90.1%** |
| 상위 20개 | 96.3% |
| 상위 50개 | 99.6% |

- 등록 142개 중 **실제로 쓰인 것은 95개**. 47개는 7일간 한 번도 호출되지 않았다.
- `ToolSearch` 가 이미 **1,224회(2.9%)** 호출되고 있다. 검색 방식은 이 시스템에
  이미 들어와 동작 중이다 — 새 개념 도입이 아니라 적용 범위를 넓히는 일이다.

---

## 3. 세 방식 비교

대표님이 물으신 셋을 실측에 비춰 정리한다.

| | 묶음(bundle) | 선별(selective) | 상주+검색 |
|---|---|---|---|
| 상주 토큰 | 중간 (묶음당 30~50개) | 최소 | **최소** |
| 경계 밖 작업 | **실패** | 선별 오류 시 실패 | 검색으로 해결 |
| 턴 중간에 필요해지면 | 불가 | **불가** | **가능** |
| 도구가 300개로 늘면 | 묶음 재설계 | 선별 비용 증가 | **프롬프트 불변** |
| 추가 왕복 | 없음 | 없음 | 9% 턴에서 1회 |
| 사람이 유지할 것 | 묶음 정의표 | 선별 규칙 | **없음** |

**묶음의 결정적 약점** — 경계를 사람이 미리 정해야 한다. 2026-09-16 하루만 봐도
"채팅 느림 조사"가 DB 조회 → 로그 분석 → 코드 수정 → 배포로 번졌다. 어느 묶음에도
맞지 않는다.

**선별의 결정적 약점** — 턴이 시작된 뒤에는 바꿀 수 없다. 질문만 보고 고르는데,
실제로 필요한 도구는 조사를 해 봐야 안다.

**결론: 상주 + 검색.** 단, 상주를 0으로 두지 않는다 — 호출의 57%가 도구 하나
(`run_remote_command`)라 그것까지 검색하게 하면 거의 모든 턴에 왕복이 하나씩 붙는다.
**자주 쓰는 것은 손에 들고 있어야 한다.**

## 4. 설계

### 4-1. 세 층

```
① 상주 10개        항상 프롬프트에 실린다          7,443자
② 이름 목록 132개  이름만 나열, 스키마는 없다      2,330자
③ 검색             ToolSearch 로 스키마를 그때 로드
```

| 구성 | 자수 | 현재 대비 |
|---|---|---|
| 현재 (142개 전량) | 76,245 | 100% |
| 상주 10 + 이름 목록 132 | **9,773** | **12.8%** |
| 상주 10만 | 7,443 | 9.8% |

**이름 목록을 넣는다.** 이름만이면 2,330자로 싸고, 모델이 "그런 도구가 있는지"를
검색 없이 알 수 있어 헛검색과 "도구가 없다"는 오답을 막는다.

설명까지 넣는 안(이름+설명 80자 = 16,800자)은 **버린다.** 상주 집합(7,443자)보다
두 배 이상 비싸 목적을 잃는다.

### 4-2. 상주 목록 — 사람이 고르지 않는다

7일 호출 통계 상위 10개다. 합쳐서 호출의 **91%** 를 덮는다.

```
run_remote_command      57.1%
query_database           7.6%
query_project_database   7.1%
read_remote_file         6.5%
pipeline_runner_status   3.4%
todo_write               3.1%
patch_remote_file        2.3%
handover_write           1.0%
write_remote_file        0.9%
read_task_logs           0.6%
```

**경계는 누적 90%로 잡았다.** 더 늘려도 토큰만 늘고 왕복은 거의 줄지 않는다
(상위 8개 90.1% → 상위 20개 96.3%인데 도구 수는 2.5배).

목록은 고정이 아니다. **주 1회 실사용 통계로 자동 재계산**한다. 지금 이 10개도
제가 고른 것이 아니라 통계가 정한 것이다.

### 4-3. 동작

```
모델: 상주 10개로 처리 가능한가?
  ├ 예 → 그대로 호출 (턴의 91%)
  └ 아니오 → 이름 목록에 있나?
        ├ 있다 → ToolSearch("select:<이름>") → 스키마 로드 → 호출
        └ 없다 → ToolSearch("<키워드>") → 후보 제시 → 로드 → 호출
```

상주 도구 설명에 **"여기 없으면 이름 목록에서 찾아 ToolSearch 로 불러와라"** 를
명시한다. 모델이 검색을 안 쓰고 "도구가 없다"고 답하는 것이 이 설계의 유일한
실패 모드다.

## 5. 구현

| # | 작업 | 대상 |
|---|---|---|
| T1 | 브리지에 `tools/list` 필터 추가 — 상주 목록 + 이름 목록 반환 | `mcp_servers/aads_tools_bridge` |
| T2 | 상주 목록을 환경변수·DB 로 주입 (하드코딩 금지) | 〃 |
| T3 | `ToolSearch` 로 비상주 도구 스키마 로드 경로 확인·보강 | 〃 |
| T4 | 릴레이가 필터 모드를 켜고 끌 수 있게 (`AADS_TOOL_RESIDENT_MODE`) | `scripts/claude_relay_server.py` |
| T5 | 주 1회 상주 목록 재계산 배치 | `scripts/` + cron |
| T6 | "검색했으나 못 찾음" 사건 기록 | 브리지 |

**T4가 안전장치다.** 기존 경로를 지우지 않고 환경변수로 전환한다. 문제가 보이면
값 하나 되돌리고 릴레이만 재기동하면 원상복구된다.

## 6. 검증 — 효과를 숫자로 비교한 뒤에만 켠다

같은 프롬프트를 두 구성으로 돌려 비교한다.

| 항목 | 기준 |
|---|---|
| 프롬프트 크기 | 76,245자 → 10,000자 이하 |
| 첫 토큰까지 | 현재 평균 39.9초 대비 단축폭 측정 |
| 기능 동일성 | 비상주 도구가 필요한 시나리오에서 ToolSearch 로 도달하는가 |
| 헛검색 | 상주로 되는 일에 검색을 쓰지 않는가 |
| 왕복 증가 | 검색 왕복이 전체 턴의 10% 이하인가 |

**켜는 순서**: 내부 테스트 세션 1개 → 문제 없으면 신규 세션 → 전체.
각 단계에서 위 지표를 다시 잰다.

## 7. 위험

| 위험 | 대응 |
|---|---|
| 모델이 검색을 안 쓰고 "도구 없음"으로 답함 | 이름 목록을 함께 실어 존재를 알린다. 상주 설명에 검색 지침 명시. 실패 시 1회 자동 재시도 |
| 검색 왕복으로 오히려 느려짐 | 상주 10개가 91%를 덮어 왕복은 9% 턴에서만. 그 왕복은 1~2초 |
| 상주 목록이 현실과 어긋남 | 주 1회 자동 재계산 + "못 찾음" 로그로 보정 |
| 되돌려야 할 때 | `AADS_TOOL_RESIDENT_MODE=0` + 릴레이 재기동 |
